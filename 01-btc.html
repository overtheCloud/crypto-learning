1. 货币、信任与双花问题

1.1 电子现金的三个必要属性

在动手写代码之前，必须先想清楚比特币到底解决了什么问题。假设你要设计一种「电子现金」，它至少需要三个属性：

属性含义传统方案怎么做
可验证所有权只有拥有者能花掉这笔钱银行核对账户密码 / 签名
防伪造不能凭空造出余额央行垄断发行 + 银行账本
防重复花费同一笔钱不能花两次银行维护唯一账本，实时扣减

前两个属性用密码学就能解决：非对称加密（公钥私钥）天然提供「可验证所有权」——用私钥签名，任何人用公钥验签；防伪造可以用一套明确的发行规则约束。唯一的难点是第三个：防重复花费。

1.2 什么是双花（Double Spending）

物理现金天生防双花：一张纸币交给对方后，你手里就没有了，「转移」和「删除」是同一个原子动作。但数字信息的本质是可复制。假设 Alice 有一个签名过的数据包 "我把 1 币转给 Bob"，她完全可以再造一个 "我把同一枚 1 币转给 Carol"，两个数据包的签名都完全有效。

双花的本质：数字签名只能证明「这条消息是我发出的」，无法证明「这是我第一次花这笔钱」。签名解决了授权，但解决不了顺序。要判断哪笔先发生，就必须有一个全网公认的时间顺序。

1.3 中心化方案与它的代价

传统方案是引入一个可信第三方（银行 / 支付公司）：所有交易都发给它，由它维护唯一账本、决定先后顺序。这个方案有效，但代价是：

  • 单点信任：第三方可以冻结、审查、篡改，也可能被攻击或倒闭。
  • 不可逆性缺失：由于支付可被撤销，商家必须索取更多客户信息、承担欺诈风险，小额支付成本被抬高。
  • 成本与延迟：跨境结算需要多层中介，T+1、T+3 结算是常态。
「商业活动在互联网上几乎完全依赖金融机构作为可信第三方来处理电子支付……需要的是一个基于密码学证明而非信任的电子支付系统。」——《比特币白皮书》引言

1.4 比特币的思路：把「谁先发生」变成一场公开竞赛

比特币的核心创新不是数字签名（1970 年代就有），也不是电子货币（DigiCash、b-money、Hashcash 都更早），而是：在没有身份、没有准入、参与者可自由进出且可能作恶的网络中，让所有诚实节点自发地对「交易的先后顺序」达成一致。

做法可以概括为四层：

① 广播 + 时间戳链

所有交易公开广播。把交易打包成「区块」，每个区块包含上一个区块的哈希，形成不可回溯修改的链条。

② 工作量证明（PoW）

生成区块必须消耗真实算力（找到满足难度的哈希）。修改历史需要重做之后所有区块的工作量。

③ 最长链规则

节点始终认可累积工作量最大的那条链。「投票权」按算力而非按 IP 数量计算，从而抵抗女巫攻击。

④ 激励相容

出块奖励 + 手续费让矿工诚实挖矿比攻击更赚钱。安全性最终由经济理性保证。

2. 白皮书 9 章逐节精读

白皮书正文只有 8 页 9 节 + 结论，是理解比特币最高性价比的材料。下面逐节浓缩要点，建议对照原文阅读。

2.1 Introduction（引言）

提出问题：互联网商业依赖金融机构做可信第三方，导致交易可逆、成本高、需要过度收集信息。目标是构建基于密码学证明而非信任的点对点支付系统。方案的关键是一个使用点对点分布式时间戳服务器生成的、按时间顺序排列的交易记录的计算证明。

2.2 Transactions（交易）

定义「电子硬币」= 一条数字签名链。上一任所有者对「上一笔交易的哈希 + 下一任所有者的公钥」签名，附在币的后面。收款人可以验证整条签名链的所有权。

关键洞察：签名链能证明所有权转移的合法性，但收款人无法确认前任是否已经把同一枚币花给了别人。所以必须让所有交易公开、并让所有人对「哪笔先到」达成共识。这句话直接推导出后面所有章节的必要性。

2.3 Timestamp Server（时间戳服务器）

做法：把一批数据的哈希打上时间戳并广泛发布，证明这些数据在该时刻已存在。每个时间戳把前一个时间戳纳入自己的哈希中，形成链条——后面的时间戳强化前面的时间戳。这就是「区块链」的雏形。

2.4 Proof-of-Work（工作量证明）

为了在 P2P 网络中实现分布式时间戳，采用类似 Hashcash 的 PoW：在区块中加入一个 nonce，不断递增直到区块哈希的前若干位为 0。特点：

  • 难求易验：找到解需要平均尝试 2^n 次，验证只需一次哈希。
  • 不可撤销的成本：区块一旦确定，修改它必须重做它以及之后所有区块的 PoW。
  • 一 CPU 一票：多数决策按算力计，避免「一 IP 一票」被伪造身份操纵。
  • 难度自适应：难度按移动平均调整，补偿硬件进步与算力变化，维持恒定出块速度。

2.5 Network（网络）

节点运行步骤（原文 6 步，务必记住）：

  1. 新交易向全网广播。
  2. 每个节点把新交易收集进一个区块。
  3. 每个节点为自己的区块寻找 PoW 解。
  4. 找到解后向全网广播该区块。
  5. 节点只在区块内所有交易有效且未被双花时接受该区块。
  6. 节点通过在该区块哈希之上继续构建下一个区块，来表达对它的接受。

节点始终认为最长链是正确的，并持续在其上工作。若同时收到两个版本，先在收到的那个上工作，同时保留另一个分支；一旦某分支变长就切换过去。丢失的区块广播是可容忍的——节点收到下一个区块发现缺失时会主动请求。

2.6 Incentive（激励）

区块的第一笔交易创建新币，归出块者所有（即 coinbase 交易）。这既是发行机制（类似金矿开采投入资源来增加流通量），也是让节点保持诚实的激励。当发行结束后，激励完全由交易手续费构成。

经济学论证：如果攻击者掌握了超过半数算力，他可以选择偷回自己的付款，或者用同样的算力老老实实挖矿获得新币。白皮书认为「按规则玩」通常更有利可图，因为攻击行为会摧毁他自身财富所依赖的系统价值。

2.7 Reclaiming Disk Space（回收磁盘空间）

一旦某个区块中的交易被足够多的后续区块掩埋，可以丢弃已花费的交易以节省空间。做法是把交易组织成 Merkle 树，只需保留树根，内部节点可以剪掉。区块头仅 80 字节，即便每 10 分钟一个区块，一年也只有约 4.2 MB 的区块头数据。

2.8 Simplified Payment Verification（简化支付验证，SPV）

轻客户端无需保存完整区块链：只保留最长链的区块头，向网络请求某交易所在的 Merkle 分支，即可验证该交易已被打包。轻客户端不能自己验证交易合法性，但看到网络节点已接受它、且后续有区块继续追加，即可获得较高置信度。

2.9 Combining and Splitting Value（价值的合并与拆分）

为避免为每一分钱单独建立交易，交易允许多输入多输出：多个输入合并小额资金，输出通常是两个——一个给收款方，一个作为找零返还给自己。这一节直接定义了 UTXO 的用法。

2.10 Privacy（隐私）

传统模式靠限制访问账本来保护隐私；比特币的账本是公开的，隐私来自把公钥与真实身份解耦（假名性）。建议：每笔交易使用新的密钥对，避免地址复用把多笔交易关联到同一主体。多输入交易仍会不可避免地暴露「这些输入属于同一所有者」。

2.11 Calculations（计算）

用赌徒破产问题建模攻击者追赶诚实链的概率。结论：只要攻击者算力占比 q < 0.5，其成功追上 z 个确认的概率随 z 指数级下降。这正是「等 6 个确认」的理论来源。

3. PoW、最长链与挖矿经济学

3.1 挖矿到底在算什么

挖矿 = 反复对 80 字节的区块头做双重 SHA-256，直到结果小于目标值 target。区块头字段固定，矿工可改动的主要是 nonce（4 字节）、时间戳、以及 coinbase 交易中的 extranonce（改动它会改变 Merkle 根）。

# 挖矿条件（概念表达）
SHA256(SHA256(block_header)) < target

# target 与难度 difficulty 的关系
difficulty = difficulty_1_target / current_target

# 期望尝试次数
expected_hashes = 2**256 / (target + 1)

下面是一个可以直接运行的极简 PoW 演示，帮助你在本机上「感受」难度的指数增长：

// mini-pow.js —— 用 Node.js 内置 crypto 演示工作量证明
// 运行：node mini-pow.js
const crypto = require('crypto');

// 双重 SHA-256，这是比特币区块头与 txid 使用的哈希函数
function hash256(buf) {
  const h1 = crypto.createHash('sha256').update(buf).digest();
  return crypto.createHash('sha256').update(h1).digest();
}

// 模拟"挖矿"：找到使哈希十六进制前缀有 zeroHexDigits 个 0 的 nonce
function mine(dataStr, zeroHexDigits) {
  const prefix = '0'.repeat(zeroHexDigits);   // 目标前缀，例如 '00000'
  const t0 = Date.now();
  let nonce = 0;
  while (true) {
    // 把业务数据与 nonce 拼接后哈希，等价于「区块头 + nonce」
    const digest = hash256(Buffer.from(dataStr + nonce)).toString('hex');
    if (digest.startsWith(prefix)) {
      const ms = Date.now() - t0;
      return { nonce, digest, ms, hashRate: Math.round(nonce / (ms / 1000)) };
    }
    nonce++;   // 唯一能做的事就是穷举，这就是"工作量"
  }
}

// 难度每增加 1 个十六进制 0，期望尝试次数就乘以 16
for (let d = 1; d <= 6; d++) {
  const r = mine('height=800000|prev=abc123|merkle=def456|', d);
  console.log('难度(前导0)=' + d, '| nonce=' + r.nonce, '| 耗时=' + r.ms + 'ms',
              '| 算力≈' + r.hashRate + ' H/s\n  hash=' + r.digest);
}
动手体会：运行上面代码，把难度从 5 提到 7，耗时大约会变成 256 倍。真实比特币网络当前难度对应的前导零远超 19 个十六进制位，全网算力在 EH/s（10^18 H/s）量级——这就是「不可篡改」的物理基础。

目标出块间隔10 分钟兼顾传播延迟与确认速度

3.3 减半与总量

初始出块奖励 50 BTC，每 210000 个区块（约 4 年）减半，用整数运算实现：

// halving.js —— 计算任意高度的出块奖励与累计发行量
function subsidy(height) {
  const halvings = Math.floor(height / 210000);
  if (halvings >= 64) return 0;          // 64 次减半后归零
  // 5,000,000,000 聪 = 50 BTC，用位移实现整数减半（与 Bitcoin Core 一致）
  return Math.floor(5000000000 / Math.pow(2, halvings));
}

function totalSupplyAt(height) {                 // 累计发行量（单位：聪）
  let total = 0;
  for (let h = 0; h <= height; h++) total += subsidy(h);
  return total;
}

for (const h of [0, 210000, 420000, 630000, 840000, 1050000]) {
  console.log('高度 ' + h, '| 奖励 = ' + (subsidy(h) / 1e8) + ' BTC',
              '| 第' + (Math.floor(h / 210000) + 1) + '期');
}
console.log('至高度 840000 累计发行 ≈ ' + (totalSupplyAt(840000) / 1e8).toFixed(2) + ' BTC');

总量上限 = 各期奖励 × 210000 求和 ≈ 20999999.98 BTC，通常记作 2100 万枚。最小单位是 聪（satoshi），1 BTC = 100,000,000 聪。

开发铁律：金额计算永远用聪做整数运算，绝不用浮点数表示 BTC。0.1 + 0.2 !== 0.3 这种误差在资金系统里是致命的。bitcoinjs-lib v6 用 number 表示聪（安全整数范围内足够，2100 万 BTC = 2.1e15 聪 < 2^53），v7 改为 bigint。

4. UTXO 模型：比特币的会计系统

4.1 没有「余额」，只有「未花费的输出」

比特币账本里不存在账户余额字段。链上只有一个巨大的集合：UTXO set（Unspent Transaction Output，未花费交易输出）。每个 UTXO 是一张不可分割的「面额不定的电子支票」，包含两个关键信息：

  • value：金额（单位：聪）。
  • scriptPubKey：锁定脚本，规定了「满足什么条件才能花掉我」。

钱包显示的「余额」是客户端算出来的：余额 = 属于我的所有 UTXO 的 value 之和。

4.2 输入、输出与找零

一笔交易做的事就是：销毁若干旧 UTXO（作为输入），创建若干新 UTXO（作为输出）。铁律有三条：

① 输入必须整花

UTXO 不能部分使用。要花 0.3，但手上只有一个 1.0 的 UTXO，就必须把整个 1.0 花掉。

② 差额靠找零

多出来的钱要新建一个输出转回自己控制的地址，这叫「找零输出（change）」。

③ 手续费是差额

fee = 输入总额 − 输出总额。它不是字段，是算出来的，由矿工在打包时取走。

最经典的新手事故：忘记加找零输出。假设你花掉一个 1 BTC 的 UTXO 只给对方 0.01 BTC，剩下的 0.99 BTC 会全部变成手续费送给矿工，且不可撤销。写转账代码时，找零计算必须有单元测试覆盖。

4.3 与银行账户模型对比

余额来源直接读取字段扫描并累加自己的 UTXO
转账语义A 余额 −x，B 余额 +x（读改写）销毁旧 UTXO，创建新 UTXO（不可变）

状态膨胀账户数增长UTXO 数增长，粉尘 UTXO 是负担
编程复杂度低（改数字）高（要做币选择、找零、费率估算）
智能合约全局共享状态，易写复杂逻辑脚本仅约束单个 UTXO 的花费条件

4.4 币选择（Coin Selection）

钱包必须决定「用哪几个 UTXO 凑出这笔付款」，这个算法直接影响手续费和隐私：

策略做法优点缺点
Largest First先用最大的 UTXO输入数少，交易体积小迅速把大额打碎，隐私差
Smallest First先用最小的能清理粉尘 UTXO输入多、体积大、费用高
Branch and Bound搜索恰好无需找零的组合（Bitcoin Core 默认）省掉找零输出，费用最低、隐私最好实现复杂，不总能找到解
Knapsack / 随机随机组合逼近目标额实现简单，抗分析结果不稳定

币选择的核心难点在于「手续费依赖输入个数，而输入个数又依赖手续费」这个循环依赖。解法是边加输入边重算费用，完整实现见第 13 节的 selectCoins，其判定条件为：

// 累加法选币的两个终止条件（完整代码见第 13 节）
const DUST = 294;                                     // P2WPKH 粉尘阈值(聪)
const feeWithChange = estimateVsize(n, 2) * feeRate;  // 需要找零：2 个输出
const feeNoChange   = estimateVsize(n, 1) * feeRate;  // 无需找零：1 个输出

// 条件 A：够付款+手续费，但余额产生的找零是粉尘 → 不建找零，差额并入手续费
if (sum >= target + feeNoChange && sum < target + feeWithChange + DUST) { /* 无找零 */ }

// 条件 B：够付款+手续费+一个有经济意义的找零 → 建找零输出
if (sum >= target + feeWithChange + DUST) { change = sum - target - feeWithChange; }

// 恒等式（必须写成断言）：Σ输入 === 付款额 + 找零 + 手续费

5.2 字段逐个解释

字段含义开发者必须注意
txid交易标识符 = 双 SHA-256(不含见证数据的序列化)，显示时字节序反转API 返回的是「大端显示序」；bitcoinjs 内部 Buffer 是小端。用 Buffer.from(txid,'hex').reverse() 转换
wtxid包含见证数据的哈希SegWit 交易 txid ≠ wtxid，这是解决延展性的关键
version交易版本号用 CSV 相对时间锁必须 version ≥ 2
vin[].txid + vout合称 outpoint，唯一定位一个 UTXOoutpoint 是 UTXO 的主键，36 字节
scriptSig解锁脚本（传统交易放签名和公钥）SegWit（原生）为空；P2SH-P2WPKH 里放的是 witness program
txinwitness见证数据栈，SegWit 的签名存放处计费时按 1/4 权重折算，故 SegWit 更便宜
sequence4 字节，原设计用于交易替换，现用于 RBF 信号和相对时间锁< 0xfffffffe 表示允许 RBF（BIP125）
vout[].value输出金额低于粉尘阈值的输出会被节点拒绝中继
scriptPubKey锁定脚本，定义花费条件「地址」只是它的人类可读编码，链上存的是脚本
locktime最早生效时间：< 5e8 视为区块高度，≥ 5e8 视为 Unix 时间戳需至少一个输入 sequence ≠ 0xffffffff 才生效
vsize / weight虚拟体积与权重费率单位是 sat/vB，不是 sat/byte
weight 与 vsize 的公式：
weight = base_size × 3 + total_size，其中 base_size 是去掉见证数据的序列化长度，total_size 是含见证数据的长度。
vsize = ceil(weight / 4)。区块上限是 4,000,000 weight units（约等于 1MB 非见证 + 折算见证）。

5.3 coinbase 交易的特殊性

  • 每个区块的第一笔交易，只有一个输入，其 outpoint 为全 0 + 0xffffffff。
  • scriptSig 位置改为 coinbase 字段（2–100 字节），可任意填内容（创世块里写了泰晤士报标题）。
  • 输出金额 ≤ 出块补贴 + 区块内所有交易手续费。
  • 成熟期 100 个区块：coinbase 输出必须等 100 个确认后才能花费，防止链重组导致的凭空花费。

6. 地址演进与脚本模板对照

6.1 为什么会有这么多种地址

地址不是账号，而是「锁定脚本」的人类可读编码。比特币的地址格式演进史，本质是脚本模板与编码方式的升级史：从「直接锁公钥」到「锁公钥哈希」（更短、可 pre-quantum 保护），再到「锁任意脚本的哈希」（P2SH，把复杂度转移给花费方），再到 SegWit（修延展性、降费用），最后到 Taproot（Schnorr 签名、脚本树、更好隐私）。

7.2 Merkle 树与 Merkle 证明

Merkle 树把 N 笔交易的 txid 两两哈希，逐层向上合并到唯一的根。它提供两个能力：完整性（改任何一笔交易，根就变）和可压缩证明（只需 log2(N) 个哈希即可证明某交易在树中）。

// merkle.js —— 构建 Merkle 根并生成/验证 Merkle 证明
const crypto = require('crypto');

const h256 = (b) =>
  crypto.createHash('sha256').update(crypto.createHash('sha256').update(b).digest()).digest();

// 注意：比特币内部用小端(内部序)哈希做树运算，txid 显示时是反转后的字节序
function buildMerkle(txidsHexDisplay) {
  let level = txidsHexDisplay.map(h => Buffer.from(h, 'hex').reverse());  // 显示序→内部序
  const tree = [level];
  while (level.length > 1) {
    const next = [];
    for (let i = 0; i < level.length; i += 2) {
      // 奇数个节点时最后一个与自身配对（比特币特有规则，也是 CVE-2012-2459 的根源）
      const right = (i + 1 < level.length) ? level[i + 1] : level[i];
      next.push(h256(Buffer.concat([level[i], right])));
    }
    level = next; tree.push(level);
  }
  return { root: level[0].reverse().toString('hex'), tree };
}

// 为第 index 笔交易生成证明路径：每层只需记录"兄弟哈希 + 它在左还是右"
function merkleProof(tree, index) {
  const proof = [];
  let idx = index;
  for (let d = 0; d < tree.length - 1; d++) {
    const level = tree[d];
    const isRight = idx % 2 === 1;
    const sib = isRight ? idx - 1 : Math.min(idx + 1, level.length - 1);
    proof.push({ hash: level[sib].toString('hex'), position: isRight ? 'left' : 'right' });
    idx = Math.floor(idx / 2);
  }
  return proof;
}

// 轻客户端拿证明重算根，与区块头里的 merkle_root 比对
function verifyProof(txidDisplay, proof, expectedRootDisplay) {
  let cur = Buffer.from(txidDisplay, 'hex').reverse();
  for (const s of proof) {
    const sib = Buffer.from(s.hash, 'hex');
    cur = s.position === 'left' ? h256(Buffer.concat([sib, cur])) : h256(Buffer.concat([cur, sib]));
  }
  return cur.reverse().toString('hex') === expectedRootDisplay;
}

const txids = ['11', '22', '33', '44', '55'].map(x => x.repeat(32));   // 5 笔假交易
const { root, tree } = buildMerkle(txids);
const proof = merkleProof(tree, 2);
console.log('Merkle 根 =', root);
console.log('证明长度 =', proof.length, '(交易总数 =', txids.length, ') | 验证 =',
            verifyProof(txids[2], proof, root));
为什么 SPV 有用：假设一个区块有 4096 笔交易，证明某笔交易被包含只需 12 个哈希（384 字节），而不是下载整个区块（可达 1–4 MB）。手机钱包正是靠这个跑起来的。

8. 确认数、链重组与最终性

8.1 确认数的含义

「N 个确认」= 包含该交易的区块之上又累积了 N−1 个区块。0 确认表示交易只在内存池（mempool）中，随时可能被替换或丢弃。

确认数典型场景风险评估
0咖啡等极小额、闪电网络入口可被 RBF 替换或双花，需额外风控
1小额支付约 10 分钟，遭遇 1 块重组概率不可忽略
3中等金额常见交易所充值门槛
6大额、行业惯例约 1 小时，白皮书计算的安全区
100coinbase 输出解锁协议强制

8.2 链重组（Reorg）与孤块

两个矿工几乎同时出块时，网络暂时分叉。下一个区块出现后，较短的分支被抛弃，其中的交易回到内存池等待重新打包，这个过程叫 reorg。

钱包/交易所后端必须处理 reorg：
  • 不要在收到区块时就把充值记为「不可逆到账」；要记录该交易所在的 block hash。
  • 每次新区块到来时检查父哈希是否与本地记录一致；不一致说明发生 reorg，需要回滚受影响高度的所有入账并重新扫描。
  • 把「确认数」作为状态机字段持久化，而不是每次请求时临时计算。
// reorg-guard.js —— 后端处理链重组的核心思路（伪实现，含中文注释）
class DepositTracker {
  constructor(minConfirm = 6) {
    this.minConfirm = minConfirm;
    this.blockIndex = new Map();   // height -> blockHash，本地认知的链
    this.deposits = new Map();     // txid -> {height, blockHash, status}
  }

  onNewBlock(height, blockHash, prevHash, tipHeight) {   // 每收到一个新区块头时调用
    const knownPrev = this.blockIndex.get(height - 1);
    if (knownPrev && knownPrev !== prevHash) {            // 父哈希不符 → 发生重组
      console.warn('检测到链重组，回滚高度 >= ' + (height - 1));
      this.rollbackFrom(height - 1);
    }
    this.blockIndex.set(height, blockHash);
    this.refreshConfirmations(tipHeight);
  }

  rollbackFrom(fromHeight) {     // 受影响高度的入账退回 pending，并清理链索引
    for (const [h] of this.blockIndex) if (h >= fromHeight) this.blockIndex.delete(h);
    for (const [txid, d] of this.deposits) {
      if (d.height >= fromHeight) {
        d.status = 'pending';    // 关键：已确认的入账必须能退回未确认
        d.height = null; d.blockHash = null;
        console.warn('入账 ' + txid.slice(0, 12) + '... 因重组回退为 pending');
      }
    }
  }

  refreshConfirmations(tipHeight) {
    for (const [, d] of this.deposits) {
      if (d.height == null) continue;
      const conf = tipHeight - d.height + 1;
      d.status = conf >= this.minConfirm ? 'confirmed' : 'confirming';
    }
  }
}

9. 手续费市场：sat/vB 竞价

9.1 费率而非总额

矿工的区块空间有限（4M weight units），他要最大化收益，所以按单位体积的收益排序打包。因此：

费率 = 手续费 ÷ vsize

单位 sat/vB。付 10000 聪但体积 1000 vB（10 sat/vB）的交易，优先级低于付 3000 聪但体积 150 vB（20 sat/vB）的交易。

手续费不是字段

fee = Σ输入 − Σ输出，隐式存在。构建交易时必须自己精确计算，多算的部分永久归矿工。

// fee.js —— 费率估算：拉取推荐费率并计算不同地址类型的成本差异
const VSIZE = {
  overhead: 11,
  in:  { p2pkh: 148, 'p2sh-p2wpkh': 91, p2wpkh: 68, p2tr: 57.5 },
  out: { p2pkh: 34, p2sh: 32, p2wpkh: 31, p2wsh: 43, p2tr: 43 }
};

function estimateFee({ inputs, outputs, feeRate }) {
  let vsize = VSIZE.overhead;
  for (const t of inputs)  vsize += VSIZE.in[t];
  for (const t of outputs) vsize += VSIZE.out[t];
  vsize = Math.ceil(vsize);
  return { vsize, fee: Math.ceil(vsize * feeRate) };
}

9.3 粉尘（Dust）阈值

如果一个输出的金额低于「花掉它所需的手续费」，它就是经济上无意义的粉尘。Bitcoin Core 默认以 3 sat/vB 计算：P2PKH 输出阈值约 546 聪，P2WPKH 约 294 聪。低于阈值的输出会被节点判为非标准交易而拒绝中继。

13. 代码③：PSBT 构建并广播 P2WPKH 转账（本篇核心）

这是全篇最重要的一段代码。它完整走完一笔转账的生命周期：选币 → 估费 → 构建 PSBT → 签名 → 验签 → finalize → 提取原始交易 → 广播。请逐行读注释。

// 03-send-p2wpkh.js —— 用 PSBT 构建、签名并广播一笔原生 SegWit 转账
// 运行：node 03-send-p2wpkh.js "助记词..." tb1q收款地址 20000
const bip39 = require('bip39');
const { bitcoin, bip32, ECPair, ecc, NETWORK } = require('./setup');
const { fetchUtxos, fetchFeeRates, broadcast } = require('./02-fetch-utxo');

const DERIVE_PATH = "m/84'/1'/0'/0/0";   // 测试网 BIP84 首地址
const DUST = 294;                        // P2WPKH 粉尘阈值

// ---------- 工具：估算 vsize（仅含 P2WPKH 输入/输出）----------
const estimateVsize = (inCount, outCount) => Math.ceil(10.5 + 68 * inCount + 31 * outCount);

// ---------- 工具：从大到小累加选币 ----------
function selectCoins(utxos, target, feeRate) {
  // 稳妥起见只用已确认 UTXO；从大到小排序以减少输入个数
  const spendable = utxos.filter(u => u.status.confirmed).sort((a, b) => b.value - a.value);
  const picked = [];
  let sum = 0;
  for (const u of spendable) {
    picked.push(u); sum += u.value;
    const feeWithChange = estimateVsize(picked.length, 2) * feeRate;
    const feeNoChange   = estimateVsize(picked.length, 1) * feeRate;
    // 剩余太少，不值得建找零输出 → 全部差额给矿工
    if (sum >= target + feeNoChange && sum < target + feeWithChange + DUST) {
      return { inputs: picked, change: 0, fee: sum - target,
               vsize: estimateVsize(picked.length, 1) };
    }
    if (sum >= target + feeWithChange + DUST) {
      return { inputs: picked, change: sum - target - Math.ceil(feeWithChange),
               fee: Math.ceil(feeWithChange), vsize: estimateVsize(picked.length, 2) };
    }
  }
  throw new Error('余额不足。可用 ' + sum + ' 聪，需要至少 ' + (target + 500) + ' 聪');
}

async function main() {
  const [mnemonic, toAddress, amountStr] = process.argv.slice(2);
  if (!mnemonic || !toAddress || !amountStr) {
    console.error('用法: node 03-send-p2wpkh.js "助记词" <收款地址> <金额(聪)>');
    process.exit(1);
  }
  const amount = parseInt(amountStr, 10);
  if (!Number.isInteger(amount) || amount <= DUST) throw new Error('金额必须为大于粉尘阈值的整数聪');

  // ===== 步骤 1：恢复密钥 =====
  if (!bip39.validateMnemonic(mnemonic)) throw new Error('助记词校验失败');
  const node = bip32.fromSeed(bip39.mnemonicToSeedSync(mnemonic), NETWORK).derivePath(DERIVE_PATH);
  // 用 ECPair 包一层，得到统一的 sign/verify 接口
  const keyPair = ECPair.fromPrivateKey(node.privateKey, { network: NETWORK });
  const payment = bitcoin.payments.p2wpkh({ pubkey: keyPair.publicKey, network: NETWORK });
  const fromAddress = payment.address;
  console.log('发送方地址 =', fromAddress);

  // ===== 步骤 2：拉取 UTXO 与费率 =====
  const utxos = await fetchUtxos(fromAddress);
  if (!utxos.length) throw new Error('该地址没有 UTXO，请先领取测试币');
  const feeRate = (await fetchFeeRates()).halfHourFee;   // 也可用 fastestFee / economyFee
  console.log('可用 UTXO =', utxos.length, '个 | 采用费率 =', feeRate, 'sat/vB');

  // ===== 步骤 3：选币与算账 =====
  const sel = selectCoins(utxos, amount, feeRate);
  const inputSum = sel.inputs.reduce((s, u) => s + u.value, 0);
  console.log('\n--- 交易账目 ---');
  console.log('输入合计   :', inputSum, '聪 (' + sel.inputs.length + ' 个输入)');
  console.log('支付给对方 :', amount, '聪');
  console.log('找零       :', sel.change, '聪');
  console.log('手续费     :', sel.fee, '聪 | 预估 vsize =', sel.vsize, 'vB',
              '| 实际费率 ≈', (sel.fee / sel.vsize).toFixed(2), 'sat/vB');
  // 账目守恒校验：这一行能挡住绝大多数资金事故
  if (inputSum !== amount + sel.change + sel.fee) throw new Error('账目不平，拒绝构建交易');

  // ===== 步骤 4：构建 PSBT =====
  const psbt = new bitcoin.Psbt({ network: NETWORK });
  psbt.setVersion(2);        // version 2 才支持 BIP68 相对时间锁
  psbt.setLocktime(0);       // 0 = 不设绝对时间锁
  for (const u of sel.inputs) {
    psbt.addInput({
      hash: u.txid,          // bitcoinjs 接受显示序 hex 字符串，内部自动反转字节序
      index: u.vout,
      // SegWit 输入只需 witnessUtxo（被花费输出的脚本+金额），BIP143 要求它们参与签名哈希
      witnessUtxo: { script: payment.output,   // 即 0014<pubKeyHash>
                     value: u.value },         // v6 用 number(聪)；v7 改为 bigint
      sequence: 0xfffffffd   // 开启 RBF：允许后续用更高费率替换本交易（BIP125）
    });
  }
  psbt.addOutput({ address: toAddress, value: amount });   // 输出 1：收款方
  // 输出 2：找零。真实钱包应改用找零链 m/84'/1'/0'/1/i 的新地址以保护隐私
  if (sel.change > 0) psbt.addOutput({ address: fromAddress, value: sel.change });
  console.log('\nPSBT(未签名, base64) =\n' + psbt.toBase64().slice(0, 120) + '...');

  // ===== 步骤 5：签名（逐输入签名，硬件钱包/离线签名器在此介入）=====
  for (let i = 0; i < sel.inputs.length; i++) psbt.signInput(i, keyPair);

  // ===== 步骤 6：验签（强烈建议，能提前发现脚本/金额错误）=====
  const validator = (pubkey, msghash, signature) =>
    ECPair.fromPublicKey(pubkey).verify(msghash, signature);
  for (let i = 0; i < sel.inputs.length; i++) {
    if (!psbt.validateSignaturesOfInput(i, validator)) throw new Error('输入 ' + i + ' 验签失败');
  }
  console.log('所有输入签名验证通过');

  // ===== 步骤 7：finalize —— 把部分签名整理成最终的 scriptSig / witness =====
  psbt.finalizeAllInputs();

  // ===== 步骤 8：提取原始交易 =====
  const tx = psbt.extractTransaction();
  const txHex = tx.toHex();
  console.log('\ntxid       =', tx.getId());
  console.log('实际 vsize =', tx.virtualSize(), 'vB | weight =', tx.weight());
  console.log('实际费率   ≈', (sel.fee / tx.virtualSize()).toFixed(2), 'sat/vB');
  console.log('原始交易 hex =\n' + txHex);

  // ===== 步骤 9：广播（加一道人工确认，避免误发）=====
  if (process.env.BROADCAST !== '1') {
    console.log('\n[未广播] 设置 BROADCAST=1 才会真正发送；也可把 hex 贴到 mempool.space 手动广播。');
    return;
  }
  const txid = await broadcast(txHex);
  console.log('\n广播成功！查看: https://mempool.space/testnet/tx/' + txid);
}

main().catch(e => { console.error('错误:', e.message); process.exit(1); });

步骤关键决策做错的后果
1 恢复密钥路径必须与地址生成时一致派生出别人的地址，签名对不上 UTXO
2 拉 UTXO是否使用未确认 UTXO父交易被替换则本交易失效

console.log('随机私钥 hex =', kp.privateKey.toString('hex'));
console.log('WIF          =', wif);
console.log('是否压缩公钥 =', kp.compressed);

// ---------- 导入：WIF → 密钥对 → 地址 ----------
const imported = ECPair.fromWIF(wif, NETWORK);
console.log('导入后公钥一致 =', imported.publicKey.equals(kp.publicKey));
console.log('对应 bc1q/tb1q 地址 =',
  bitcoin.payments.p2wpkh({ pubkey: imported.publicKey, network: NETWORK }).address);

// ---------- 解析 WIF 的字节结构 ----------
// 结构: [版本1字节][私钥32字节]([压缩标志0x01]) 再做 Base58Check（附 4 字节校验和）
function decodeWIF(wifStr) {
  const payload = bs58check.decode(wifStr);   // 自动校验并去掉 4 字节校验和
  const version = payload[0];
  return {
    版本字节: '0x' + version.toString(16),
    网络: version === 0x80 ? '主网' : (version === 0xef ? '测试网/regtest' : '未知'),
    私钥: Buffer.from(payload.subarray(1, 33)).toString('hex'),
    压缩标志: payload.length === 34 && payload[33] === 0x01
  };
}
console.log('\nWIF 解析:', decodeWIF(wif));

// ---------- 版本字节与首字符对照 ----------
// 主网未压缩 0x80 → 5...   主网压缩 0x80+0x01 → K.../L...   测试网压缩 0xef+0x01 → c...

// ---------- 从 HD 钱包导出单个 WIF（把某地址私钥交给第三方工具时用）----------
const bip39 = require('bip39');
const { bip32 } = require('./setup');
const child = bip32.fromSeed(bip39.mnemonicToSeedSync(bip39.generateMnemonic(128)), NETWORK)
                   .derivePath("m/84'/1'/0'/0/0");
console.log('HD 首地址私钥导出为 WIF =', child.toWIF());
WIF 的两个坑：① 主网 WIF 导入测试网库会因版本字节不符而报错，跨网搬运需显式指定 network；② WIF 里的压缩标志会改变生成的地址——同一把私钥，压缩公钥和非压缩公钥对应两个不同的 P2PKH 地址。早期钱包的资产丢失事故大多源于此。SegWit 只允许压缩公钥。

15. 2-of-3 多签地址（P2SH 与 P2WSH）

多签（multisig）用 OP_CHECKMULTISIG 实现「M 个签名中的任意 M 个即可花费」。2-of-3 是最常用配置：三把钥匙分散保管，丢一把不影响使用，被盗一把不损失资金。

15.1 传统多签：P2SH（地址 3... / 2...）

// 05-multisig-p2sh.js —— 创建 2-of-3 P2SH 多签地址
const { bitcoin, ECPair, NETWORK } = require('./setup');

// 三位参与者各持一把密钥（生产环境应由三方各自离线生成，只交换公钥）
const [alice, bob, carol] = [1, 2, 3].map(() => ECPair.makeRandom({ network: NETWORK }));

// 关键：公钥顺序会改变赎回脚本与地址！按字典序排序（BIP67）可保证任何人算出同一地址
const pubkeys = [alice, bob, carol].map(k => k.publicKey).sort((a, b) => Buffer.compare(a, b));

// 第 1 层：p2ms 生成裸多签脚本 OP_2 <pk1> <pk2> <pk3> OP_3 OP_CHECKMULTISIG
const p2ms = bitcoin.payments.p2ms({ m: 2, pubkeys, network: NETWORK });
// 第 2 层：包进 P2SH，链上只暴露脚本哈希，付款方看不到内部结构
const p2sh = bitcoin.payments.p2sh({ redeem: p2ms, network: NETWORK });

console.log('=== 2-of-3 P2SH 多签 ===');
console.log('地址         =', p2sh.address);                      // 主网 3... / 测试网 2...
console.log('赎回脚本 asm =', bitcoin.script.toASM(p2ms.output));
console.log('赎回脚本 hex =', p2ms.output.toString('hex'));        // 【必须备份】
console.log('锁定脚本 asm =', bitcoin.script.toASM(p2sh.output));  // OP_HASH160 <h> OP_EQUAL

// 花费时 scriptSig = OP_0 <签名A> <签名B> <赎回脚本>
// 开头的 OP_0 是为了填补 OP_CHECKMULTISIG 多弹一个栈元素的历史 bug；
// 签名顺序必须与赎回脚本中的公钥顺序一致，否则验证失败。
// 该类型单输入 vsize ≈ 297 vB（远高于 P2WPKH 的 68），费用昂贵。

15.2 隔离见证多签：P2WSH（地址 bc1q，62 字符）

// 06-multisig-p2wsh.js —— 创建 2-of-3 P2WSH 多签地址（推荐）
const { bitcoin, ECPair, NETWORK } = require('./setup');

const keys = [1, 2, 3].map(() => ECPair.makeRandom({ network: NETWORK }));
const pubkeys = keys.map(k => k.publicKey).sort((a, b) => Buffer.compare(a, b));

const p2ms = bitcoin.payments.p2ms({ m: 2, pubkeys, network: NETWORK });

// ① 原生 P2WSH：锁定脚本 = OP_0 <sha256(witnessScript)>（32 字节，故地址更长）
const p2wsh = bitcoin.payments.p2wsh({ redeem: p2ms, network: NETWORK });
console.log('=== 2-of-3 P2WSH（原生，推荐）===');
console.log('地址         =', p2wsh.address);                       // tb1q... 62 字符
console.log('见证脚本 hex =', p2ms.output.toString('hex'));
console.log('锁定脚本 asm =', bitcoin.script.toASM(p2wsh.output));
console.log('见证脚本哈希 = sha256(witnessScript)，注意不是 hash160');

// ② 嵌套 P2SH-P2WSH：兼容只能向 3... 地址付款的老钱包/老交易所
const nested = bitcoin.payments.p2sh({ redeem: p2wsh, network: NETWORK });
console.log('\n=== P2SH-P2WSH（兼容型）=== 地址 =', nested.address);  // 普通 3... 外观

// ③ 费用对比：同为 2-of-3，隔离见证便宜很多（单输入 vsize）
for (const [name, vsize, note] of [
  ['P2SH 2-of-3',        297, '签名与赎回脚本全额计费'],
  ['P2SH-P2WSH 2-of-3',  139, '见证数据 1/4 折算，外层多 35 字节'],
  ['P2WSH 2-of-3',       104, '最省，且修复了交易延展性'],
  ['P2TR (MuSig2 聚合)',  57.5, '链上看不出是多签，隐私最好']
]) console.log('  ' + name.padEnd(22) + String(vsize).padStart(6) + ' vB | ' + note);

// ④ 用 PSBT 花费 P2WSH 多签时，输入必须额外提供 witnessScript，否则无法签名/finalize
console.log('\nPSBT 输入模板 =', JSON.stringify({
  hash: '<txid>', index: 0,
  witnessUtxo: { script: '<p2wsh.output hex>', value: '<聪>' },
  witnessScript: '<p2ms.output hex>'
}));
选型建议：新项目一律用 P2WSH（或 Taproot + MuSig2）。P2SH 多签只在需要兼容老系统时使用。无论哪种，赎回脚本/见证脚本必须与私钥一起备份——只有私钥而没有脚本，资金将永久锁死。这就是输出描述符（Descriptors）被发明出来的原因，详见下一篇。

// 07-core-rpc.js —— 用内置 fetch 调用 Bitcoin Core JSON-RPC，无需额外依赖
const RPC_URL  = 'http://127.0.0.1:18443/';       // regtest 端口
const RPC_AUTH = 'Basic ' + Buffer.from('devuser:devpass').toString('base64');

// 钱包相关 RPC 需要带钱包路径，例如 /wallet/dev
async function rpc(method, params = [], wallet = '') {
  const res = await fetch(RPC_URL + (wallet ? 'wallet/' + wallet : ''), {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', Authorization: RPC_AUTH },
    body: JSON.stringify({ jsonrpc: '1.0', id: Date.now(), method, params })
  });
  const json = await res.json();
  if (json.error) throw new Error(method + ' 失败: ' + JSON.stringify(json.error));
  return json.result;
}
