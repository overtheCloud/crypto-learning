TRON 篇 I：概念与钱包开发

读懂 TRON 的资源模型与账户权限，用 Node.js 从零写出能转账、能收 USDT 的钱包。主要参考：TRON 官方开发者文档 developers.tron.network 与中文版 cn.developers.tron.network。

本章目标：
  1. 说清 TRON 的 DPoS 共识、TVM 与 EVM 的异同；
  2. 理解并能在代码里实现 hex 地址 ↔ T 开头 Base58Check 地址的互转；
  3. 吃透 Bandwidth / Energy 资源模型，能估算一笔 TRX 与一笔 TRC-20 转账的真实成本；
  4. 用 TronWeb 完成助记词派生、TRX 转账、TRC-20 余额查询与转账的完整可运行代码；
  5. 集成 TronLink、实现离线签名 + 广播分离，并避开新地址未激活、能量不足烧 TRX 等常见坑。

1. TRON 定位：高吞吐支付链

TRON 是一条 2018 年主网上线的公链，定位非常聚焦：高吞吐、低费用、面向稳定币支付。对于做过以太坊的钱包开发者，最容易记住的一句话是：“TRON 把 EVM 的精华搬了过来，但把 gas 费模型换成了资源（Bandwidth/Energy）质押模型，并把出块速度提了上来。”

几个让 TRON 在支付场景特别有存在感的事实：

  • USDT 最大流通网络之一：Tether 在 TRON 上发行的 USDT-TRC20 长期占据全网 USDT 流通量的最大份额，原因是转账快（秒级）、费用极低（资源充足时近乎免费）。
  • 亚洲 OTC 与商户支付首选：在跨境汇款、场外交易、链上收款场景中，TRX + USDT-TRC20 组合是大量钱包与交易所的底层通道。
  • EVM 兼容：你已有的 Solidity 知识基本能直接复用，只是编译器版本、地址前缀、费用模型有差异（见第 3、6 节）。
提示：本篇假设你已读完公共基础篇，懂 secp256k1、ECDSA、助记词/BIP39、HD 派生（BIP44），以及以太坊账户与合约的基本概念。我们不再重复这些，只讲 TRON 的“差异点”。

2. DPoS 共识与出块

TRON 采用 DPoS（Delegated Proof of Stake，委托权益证明），核心是一组被选举出来的出块节点。

  • 27 个超级代表（Super Representative, SR）：全网用户用 TRX 给候选人投票，票数前 27 名成为 SR，轮流负责出块。候选 SR 之外的节点称为“超级代表合伙人”（SR Partner）。
  • 投票机制：用户质押 TRX（冻结/投票）获得投票权，给候选人投票不产生消耗，但投票权随质押释放而消失，可随时改投。
  • 出块速度：约 3 秒一个区块，对比以太坊 12 秒、比特币 600 秒，这是 TRON 支付体验“快”的来源。
  • 奖励分发：每个新区块给 SR 的区块奖励（约 16 TRX/块，随参数调整）和投票奖励，SR 通常再把自己的收益按投票份额返给用户（节点分红）。
一句话记忆：以太坊是“全球矿工竞争打包”，TRON 是“27 个当选代表轮流值班”，所以更快、更省，但更中心化一些——这是取舍，不是缺陷。

对钱包开发者的直接影响：

  • 交易从广播到被打包通常 3 秒内可见，确认体验远好于 BTC；
  • 因为出块快、回滚概率高，业务上要区分“首次打包（1 确认）”与“固化（solidified，约 19 秒、约 6+ 确认）”——见第 8 节。

3. TVM 与 EVM 兼容性

TRON 的虚拟机叫 TVM（TRON Virtual Machine），它在设计上高度对齐以太坊 EVM，目标就是让 Solidity 合约“几乎无改动”地迁移过来。

维度EVM / 以太坊TVM / TRON
字节码执行EVM opcodeTVM opcode，与 EVM 高度一致，多数 opcode 相同
智能合约语言Solidity / VyperSolidity 为主（TVM 还支持部分 TVM 汇编）
计算计费Gas（ETH 支付）Energy（TRX 质押或燃烧抵扣），概念类似但获取方式不同
存储计费Gas（Storage）TRON 也有存储概念，但钱包开发更关心 Bandwidth/Energy
地址表示20 字节，0x 前缀 hex21 字节：0x41 + 20 字节公钥哈希，T 开头 Base58Check
编译器版本solc 跟进最新TVM 编译器版本相对滞后，需用受支持版本（见第 11 篇）
迁移要点：同一份 Solidity 源码，在 TronBox 里用受支持的 solc 重新编译即可部署到 TRON；但地址字面量、block.timestamp 语义、Energy 计费等细节要小心（第 11 篇有完整差异表）。

4. 地址体系：0x41 前缀与 Base58Check

这是钱包开发者最该写对的一块。TRON 的地址本质来自与以太坊完全相同的 secp256k1 公钥推导：

  1. 私钥 → 公钥（secp256k1，压缩或解压均可，取 Keccak-256 哈希）；
  2. 取公钥哈希的低 20 字节作为地址主体（和 ETH 一样）；
  3. TRON 在此 20 字节前补一个字节 0x41（ASCII “A”，代表 TRON 主网），得到 21 字节；
  4. 对这 21 字节做 Base58Check 编码（双 SHA-256 校验和 + Base58 字母表），得到以 T 开头的人类可读地址。
极易混淆：TRON 内部存储/API 用的是 41xxxx 的 hex 地址，而用户看到的是 Txxxx 的 Base58 地址。二者是同一地址的两种编码，不是两个地址。RPC 的 contract 字段里常用 hex 形式，前端展示用 T 形式。

4.1 hex ↔ base58 互转算法

算法步骤（你完全可以用纯 JS 实现，无需第三方库）：

  • hex(21B) → base58：在 21 字节前补 1 个 0x00 字节（Bitcoin 风格的 version 占位，便于 Base58Check 的 leading-zero 处理）→ 计算双 SHA256 取前 4 字节作 checksum → 拼接 [payload + checksum] → 用 Base58 字母表编码。
  • base58 → hex：Base58 解码 → 去掉末尾 4 字节 checksum（可校验）→ 去掉开头 1 字节 version（0x00）→ 得到 21 字节，首字节须为 0x41。

纯 JS 实现（仅依赖 Node 内置 crypto，无外部库）：

// tronAddress.js —— TRON 地址 hex <=> base58 互转（纯 Node 实现，无第三方库）
const crypto = require("crypto");

// Base58 字母表（与比特币相同）
const ALPHABET = "123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz";
const ALPHABET_MAP = {};
for (let i = 0; i < ALPHABET.length; i++) ALPHABET_MAP[ALPHABET[i]] = i;

function sha256(buffer) {
  return crypto.createHash("sha256").update(buffer).digest();
}

// 大数 Base58 编码（处理任意长度字节）
function base58Encode(buffer) {
  let digits = [0];
  for (let i = 0; i < buffer.length; i++) {
    let carry = buffer[i];
    for (let j = 0; j < digits.length; j++) {
      carry += digits[j] << 8;
      digits[j] = carry % 58;
      carry = (carry - digits[j]) / 58;
    }
    while (carry > 0) {
      digits.push(carry % 58);
      carry = (carry - (carry % 58)) / 58;
    }
  }
  let result = "";
  // 前导零（0x00）转为前导 '1'
  for (let i = 0; buffer[i] === 0 && i < buffer.length - 1; i++) result += "1";
  for (let k = digits.length - 1; k >= 0; k--) result += ALPHABET[digits[k]];
  return result;
}

function base58Decode(str) {
  const bytes = [0];
  for (let i = 0; i < str.length; i++) {
    const c = str[i];
    if (!(c in ALPHABET_MAP)) throw new Error("非法 Base58 字符: " + c);
    let carry = ALPHABET_MAP[c];
    for (let j = 0; j < bytes.length; j++) {
      carry += bytes[j] * 58;
      bytes[j] = carry & 0xff;
      carry >>= 8;
    }
    while (carry > 0) {
      bytes.push(carry & 0xff);
      carry >>= 8;
    }
  }
  // 前导 '1' 还原为前导 0x00
  for (let i = 0; i < str.length && str[i] === "1"; i++) bytes.push(0);
  return Buffer.from(bytes.reverse());
}

// hex(0x41 开头 21 字节) -> T 开头 base58
function hexToBase58(hex) {
  const addr = Buffer.from(hex.replace(/^0x/, ""), "hex");
  if (addr.length !== 21 || addr[0] !== 0x41) throw new Error("非法 TRON hex 地址");
  const versioned = Buffer.concat([Buffer.from([0x00]), addr]); // 补 1 字节 version
  const checksum = sha256(sha256(versioned)).slice(0, 4);
  return base58Encode(Buffer.concat([versioned, checksum]));
}

// T 开头 base58 -> hex(0x41 开头)
function base58ToHex(base58) {
  const decoded = base58Decode(base58);
  const body = decoded.slice(0, decoded.length - 4);     // 去 checksum
  const payload = body.slice(1);                          // 去 version 0x00
  if (payload.length !== 21 || payload[0] !== 0x41) throw new Error("校验失败或非 TRON 地址");
  // 校验 checksum
  const checksum = decoded.slice(decoded.length - 4);
  const calc = sha256(sha256(body)).slice(0, 4);
  if (Buffer.compare(checksum, calc) !== 0) throw new Error("Base58Check 校验和不匹配");
  return "0x" + payload.toString("hex");
}

// 使用示例
const hexAddr = "41" + "a6e56f0a3c9c1e2b4d5e6f70819a0b1c2d3e4f50"; // 21 字节
const b58 = hexToBase58(hexAddr);
console.log("base58:", b58);
console.log("back  :", base58ToHex(b58));
实战建议：生产环境直接用 TronWeb 内置的 tronWeb.address.fromHex() / toHex() 即可。上面代码的价值在于让你真正理解地址是怎么来的——面试与排查假地址攻击时极有用。

5. 账户激活机制

TRON 有一个以太坊没有的概念：新地址默认未激活（account not exist）。

  • 一个从未在链上出现过的地址，无法接收任何资产，也不能作为交易发起方，直到它被“激活”。
  • 激活方式：任意已激活地址向该新地址转入 ≥ 1 TRX（通常是恰好转 1 TRX 或 0.1 TRX 等），该笔转账本身即把目标地址“创建”到账本里。
  • 激活后，地址才有余额、资源、合约数据等状态。TRC-20 代币也只能在已激活地址间流转。
钱包开发大坑：给用户生成新充值地址后，若直接往里打 USDT（TRC-20），交易会失败，因为地址未激活。正确流程是先由热钱包向新地址转 1 TRX 激活，再转 USDT，或要求用户先用 TRX 触发一次任意交易。第 12 篇的收款系统会专门处理这一点。

6. 资源模型精讲（本篇重点）

这是 TRON 与以太坊最大的差异，也是钱包成本估算的核心。以太坊用 gas 直接烧 ETH；TRON 把链上操作需要的“资源”拆成两类：

资源用途免费额度获取方式
Bandwidth（带宽）普通转账（TransferContract）、交易字节本身的消耗每个激活账户每日约 600 B 免费带宽（按日恢复）质押 TRX 获得；不足时烧 TRX
Energy（能量）调用智能合约（TriggerSmartContract）、合约内部计算无免费额度质押 TRX 获得；不足时烧 TRX 抵扣（更贵）

6.1 为什么有“资源”而不是单纯烧币

TRON 的设计哲学是：长期持有者通过质押 TRX 换取免费资源，频繁使用者则按资源消耗燃烧 TRX。这样“网络的使用权”某种程度上回馈给生态贡献者（质押者），而不是全部销毁。对商户而言，预质押一批 TRX 换 Energy，可以让成千上万笔 USDT 转账几乎零边际成本。

6.2 Stake 2.0 质押获取资源

TRON 的资源获取经历了 Stake 1.0 → Stake 2.0 的演进。Stake 2.0 的关键改进：

  • 可以随时 delegate（委托）资源给任意其他地址，而不再像 1.0 那样只能给自己；
  • 解质押有约 14 天等待期（unstake 后资源与投票权逐步释放）；
  • 账户可同时持有“投票权”和“资源委托”，更灵活。

6.3 费用估算公式

合约调用消耗 Energy 不足时，按如下规则燃烧 TRX：

// 资源消耗与 TRX 燃烧估算（官方参数，会随链上动态调节，以下为常用量级）
// 1 Energy 约等价于 0.00028 TRX 燃烧（主网常见值，priceInTrx = SUN 计价）
// 实际单价由链上 chainParameter: getEnergyFee 决定
const ENERGY_FEE_SUN = 280;       // 1 Energy 的 TRX 燃烧价（单位 SUN，1 TRX = 1_000_000 SUN）
const TRX_PER_ENERGY = ENERGY_FEE_SUN / 1_000_000; // = 0.00028 TRX

function burnTrxFor(energyNeeded, energyOwned) {
  const shortfall = Math.max(0, energyNeeded - energyOwned);
  return shortfall * TRX_PER_ENERGY; // 需燃烧 TRX
}

// 例：一次普通 USDT transfer 约需 13000~14000 Energy
const need = 13800;
const owned = 0; // 未质押
console.log("需燃烧 TRX:", burnTrxFor(need, owned).toFixed(4), "TRX"); // ~3.86 TRX

下表为典型场景估算（实际以链上参数为准，仅作量级参考）：

操作消耗资源已质押足额资源未质押（燃烧 TRX）
TRX 普通转账（给自己/他人）~200 Bandwidth免费（用每日免费额度或质押带宽）~0.27 TRX（按 Bandwidth 单价）

6.5 查询账户资源与质押

在写钱包前，先学会“看”一个地址当前有多少资源。TronWeb 提供了账户查询，但更精确的资源数值建议直接调节点 API：

// demo-resource.js —— 查询账户资源与质押情况
const TronWeb = require("tronweb");
const tronWeb = new TronWeb({ fullHost: "https://nile.trongrid.io" });

async function showResources(addrBase58) {
  const account = await tronWeb.trx.getAccount(addrBase58);
  // account 关键字段：
  // - balance: 余额（SUN）
  // - frozen: [{ frozen_balance, expire_time }]  质押的 TRX（SUN）
  // - account_resource: { frozen_balance_for_energy, delegated_frozen_balance_for_energy, energy_window_size ... }
  // - net_window_size / free_net_usage 等带宽信息
  console.log("余额(TRX):", account.balance / 1e6);
  console.log("质押 TRX :", account.frozen
    ? account.frozen.map(f => (f.frozen_balance / 1e6)).join(", ")
    : "无");
  const ar = account.account_resource || {};
  console.log("Energy 质押:", (ar.frozen_balance_for_energy || {}).frozen_balance
    ? (ar.frozen_balance_for_energy.frozen_balance / 1e6) + " TRX" : "无");
}
showResources("T你的地址");

6.6 质押 TRX 换取 Bandwidth / Energy（Stake 2.0）

钱包里常见的“冻结/质押”按钮，本质是调用 freezeBalanceV2 把 TRX 锁住，换取资源或投票权（Stake 2.0）。解锁需等待约 14 天。

// demo-stake.js —— 质押 100 TRX 换 Energy（Stake 2.0 freezeBalanceV2）
const TronWeb = require("tronweb");
const tronWeb = new TronWeb({
  fullHost: "https://nile.trongrid.io",
  privateKey: "你的Nile私钥",
});

async function stakeForEnergy(trxAmount, resourceType = "ENERGY") {
  // freezeBalanceV2(amountSun, resourceType)
  const tx = await tronWeb.transactionBuilder.freezeBalanceV2(
    tronWeb.toSun(trxAmount),   // 质押数量（SUN）
    resourceType                // "ENERGY" 或 "BANDWIDTH"
  );
  const signed = await tronWeb.trx.sign(tx);
  const ret = await tronWeb.trx.broadcast(signed);
  console.log("质押广播:", ret);

  // 若要把资源委托给另一个地址（如归集/收款子地址），再调用 delegateResource
  // await tronWeb.transactionBuilder.delegateResource(tronWeb.toSun(trxAmount), toAddr, resourceType);
  return ret;
}
stakeForEnergy(100, "ENERGY");
商户优化思路：把一大笔 TRX（如 1000 TRX）质押换 Energy，可支撑数万笔 USDT 转账几乎零成本；若瞬时需求超过自有 Energy，还可临时租赁 Energy（第三方市场，见第 12 篇成本对比）。质押解锁的 14 天等待期是TRON 防止资源被瞬间抛售的设计。

7. 交易结构与 txID

一笔 TRON 交易（Transaction）的 JSON 结构大致如下：

// TRON 交易（TriggerSmartContract 为例）的典型结构
{
  "visible": false,                 // false=地址用 hex；true=用 base58
  "txID": "ab12...ef",              // 交易的唯一 ID（raw_data 的 SHA256）
  "raw_data": {
    "contract": [
      {
        "parameter": {
          "value": {
            "owner_address": "41xxxx",          // 调用者（hex）
            "contract_address": "41xxxx",        // 被调合约（hex）
            "data": "0xa9059cbb..."              // 编码后的函数调用（如 transfer）
          }
        },
        "type": "TriggerSmartContract"           // 合约触发类型
      }
    ],
    "ref_block_bytes": "8fa2",
    "ref_block_hash": "a1b2...",
    "expiration": 1700000000000,                 // 过期时间（毫秒）
    "timestamp": 1699999999000
  },
  "raw_data_hex": "0a...",                       // raw_data 的十六进制
  "signature": [ "3045...", ... ]                // 签名数组（多签时为多个）
}

常见 contract 类型：

  • TransferContract：TRX 转账（owner → to，amount 单位 SUN）；
  • TransferAssetContract：TRC-10 资产转账（TRC-10 是 TRON 内置代币标准，现多被 TRC-20 取代）；
  • TriggerSmartContract：触发智能合约调用（余额查询、转账、任意合约方法）；
  • AccountPermissionUpdateContract：更新账户权限/多签配置（见第 9 节）。
txID 计算：txID = SHA256(raw_data 序列化)。注意签名不改变 txID，因为 txID 只覆盖 raw_data。钱包广播前可本地先计算 txID，后续用它轮询确认状态。

8. 确认与固化（solidified）

因为 DPoS 出块快（3 秒），短距离分叉概率高于 BTC/ETH，所以 TRON 引入了固化（solidified）概念：

  • 1 确认：交易被打包进某个区块，约 3 秒可见，但理论上仍可能被回滚；
  • 固化（solidified）：交易所在区块获得足够后续区块确认（通常约 19 秒，约 6+ 区块），被视为不可逆。
业务权衡：小额/高并发场景可用“1 确认即放行”（如显示余额、发通知）；大额/充值入账建议等固化（约 19 秒）再确认为最终入账，规避短回滚风险。第 12 篇收款系统会据此设计确认策略。

9. 账户权限体系（多签）

这是 TRON 的特色能力，钱包开发（尤其企业/多签钱包）必须懂。以太坊的多签依赖合约（如 Gnosis Safe），而 TRON 把多签内建在协议层。

每个账户有三类权限：

权限作用阈值/权重
owner（所有者）最高权限，可做任何操作并修改权限结构本身可设阈值
witness仅 SR 候选人相关，普通钱包用不到—
active（活跃）日常操作权限（转账、调合约），可分散给多个 key可设阈值与多 key 权重

权限结构核心参数：

  • threshold：阈值，签名总权重 ≥ 阈值时该权限生效；
  • keys[]：每个 key 含 address（签名公钥地址）和 weight（权重）；
  • 多签 = 把多个 key 加入 active 权限，各自权重相加 ≥ 阈值。

构造一个 2-of-3 多签 active 权限的示例（用 TronWeb 设置）：

// 设置账户为 2-of-3 多签（active 权限需 3 个 key 中至少 2 个签名）
// 前提：调用者须持有 owner 权限
const owner = tronWeb.defaultAddress; // 当前 owner
const keys = [
  { address: tronWeb.address.toHex("TKeyA..."), weight: 1 },
  { address: tronWeb.address.toHex("TKeyB..."), weight: 1 },
  { address: tronWeb.address.toHex("TKeyC..."), weight: 1 },
];
const permission = {
  type: 2,                 // 2 = active 权限
  id: 2,
  permission_name: "active",
  threshold: 2,           // 需要 2 个权重
  operations: "7fffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff", // 允许全部操作
  keys: keys,
};
const tx = await tronWeb.transactionBuilder.updateAccountPermissions(
  owner.address, // 目标账户（此处为自己）
  null,          // owner 权限不修改
  permission,    // active 权限配置
  null           // witness 不修改
);
const signed = await tronWeb.trx.sign(tx); // 由 owner 签名
const ret = await tronWeb.trx.broadcast(signed);
console.log("多签配置广播结果:", ret);
企业钱包重点：TRON 协议层多签意味着多签交易本身就是一个普通交易，节点会校验签名权重；同时每笔业务交易携带多个 signature。构建离线多签钱包时，要分别收集各 key 的 signature 再合并广播（见第 18 节冷钱包思路）。

11.2 手动按 m/44'/195'/0'/0/0 派生（推荐理解）

TRON 的 BIP44 coin type 是 195（不是 ETH 的 60）。派生路径：m/44'/195'/0'/0/0。

// demo2-hd-derive.js —— 手动 BIP44 派生 TRON 地址（m/44'/195'/0'/0/0）
const TronWeb = require("tronweb");
const bip39 = require("bip39");
const HDKey = require("hdkey");

const mnemonic = "zoo zoo zoo zoo zoo zoo zoo zoo zoo zoo zoo wrong";

(async () => {
  const seed = await bip39.mnemonicToSeed(mnemonic);
  const root = HDKey.fromMasterSeed(seed);
  // TRON coin type = 195（注意硬编码单引号表示 hardened）
  const path = "m/44'/195'/0'/0/0";
  const child = root.derive(path);

  const privateKey = child.privateKey.toString("hex");
  // 用私钥构造 TronWeb（自动推出地址）
  const tronWeb = new TronWeb({
    fullHost: "https://nile.trongrid.io",
    privateKey: privateKey,
  });
  console.log("派生路径 :", path);
  console.log("私钥     :", privateKey);
  console.log("地址hex  :", tronWeb.defaultAddress.hex);
  console.log("地址base58:", tronWeb.defaultAddress.base58);
})();
务必牢记：TRON 路径的 coin type 是 195。若用 ETH 的 60，派生出的私钥在 TRON 上也能“算”出地址，但和同一助记词在以太坊生态的钱包（如 MetaMask）不一致，会造成资产错乱。跨链钱包要分别为不同链用各自的 coin type 派生。

13. TRX 转账完整流程

标准三步：构造交易 → 签名 → 广播 → 轮询确认。

// demo4-trx-transfer.js —— TRX 转账完整流程（Nile 测试网）
const TronWeb = require("tronweb");
const tronWeb = new TronWeb({
  fullHost: "https://nile.trongrid.io",
  privateKey: "你的私钥（Nile 测试私钥）",
});

async function transferTrx(toBase58, amountTrx) {
  const from = tronWeb.defaultAddress.base58;
  const amountSun = tronWeb.toSun(amountTrx); // TRX -> SUN（1 TRX = 1e6 SUN）

  // 1. 构造交易
  const tx = await tronWeb.transactionBuilder.sendTrx(toBase58, amountSun, from);
  // 2. 签名
  const signedTx = await tronWeb.trx.sign(tx, tronWeb.defaultPrivateKey);
  // 3. 广播
  const result = await tronWeb.trx.broadcast(signedTx);
  if (!result.result) throw new Error("广播失败: " + JSON.stringify(result));
  console.log("已广播 txID:", result.txid);

  // 4. 轮询确认（最多等约 30 秒，3 秒出块）
  const confirmed = await waitForConfirmation(result.txid);
  return confirmed;
}

async function waitForConfirmation(txID, timeoutMs = 30000) {
  const start = Date.now();
  while (Date.now() - start < timeoutMs) {
    const tx = await tronWeb.trx.getTransactionInfo(txID);
    if (tx && tx.receipt && tx.receipt.result === "SUCCESS") {
      return { ok: true, txID, block: tx.blockNumber };
    }
    if (tx && tx.receipt && tx.receipt.result === "FAILED") {
      return { ok: false, reason: tx.receipt.result };
    }
    await new Promise((r) => setTimeout(r, 3000)); // 每 3 秒查一次
  }
  return { ok: false, reason: "timeout（可能已打包但未固化）" };
}

transferTrx("T接收方地址", 1.5).then(console.log).catch(console.error);
注意金额单位：TRON 内部最小单位是 SUN，1 TRX = 1,000,000 SUN。构造交易务必用 tronWeb.toSun()，否则 1.5 会被当成 1.5 SUN（几乎为 0）。

14. TRC-20（USDT）实战

主网 USDT 合约地址：TXLAQ63Xg1NAzckPwKHvzw7CSEmLMEqcdjmy（TRC-20）。Nile 测试网有对应的测试 USDT 合约，可在 Tronscan Nile 上搜索 “USDT” 找到水龙头发行的测试币地址。

精度：USDT 是 6 位小数（不是 ETH 上 USDT 的 6 位，这里一致；但注意有些 TRC-20 是 18 位）。转账时 amount * 10^6。
// demo5-trc20.js —— TRC-20 (USDT) 余额查询与转账
const TronWeb = require("tronweb");
const tronWeb = new TronWeb({
  fullHost: "https://nile.trongrid.io",
  privateKey: "你的Nile私钥",
});

// 主网 USDT：TXLAQ63Xg1NAzckPwKHvzw7CSEmLMEqcdjmy
// Nile 测试网 USDT 合约地址以你水龙头页面为准，下面用变量占位
const USDT_CONTRACT = "TXLAQ63Xg1NAzckPwKHvzw7CSEmLMEqcdjmy";
const DECIMALS = 6;

async function getUsdtBalance(ownerBase58) {
  const contract = await tronWeb.contract().at(USDT_CONTRACT);
  const raw = await contract.balanceOf(ownerBase58).call(); // 只读，免 Energy
  const balance = Number(raw) / Math.pow(10, DECIMALS);
  console.log("USDT 余额:", balance);
  return balance;
}

async function transferUsdt(toBase58, amount) {
  const contract = await tronWeb.contract().at(USDT_CONTRACT);
  const amountSun = Math.floor(amount * Math.pow(10, DECIMALS));
  // transfer 是写操作，用 .send()，必须给 feeLimit（燃烧 TRX 上限，单位 SUN）
  const tx = await contract.transfer(toBase58, amountSun).send({
    feeLimit: tronWeb.toSun(20), // 最多允许燃烧 20 TRX（Energy 不足时）
  });
  console.log("USDT 转账 txID:", tx);
  return tx;
}

// 用法
getUsdtBalance("T你的地址").then(() => transferUsdt("T对方地址", 10));
feeLimit 必填：合约写操作（.send()）必须显式传 feeLimit，单位为 SUN（1 TRX = 1e6 SUN）。若不传或设太低，交易会直接失败并提示 “feeLimit too low”。建议按业务预估的 Energy 成本上浮设置（如 20~50 TRX），实际只会燃烧真实消耗部分，不会扣满。

15. 交易结果解析

广播后，用 getTransactionInfo(txID) 解析真实结果：

// demo6-receipt.js —— 解析交易回执
const info = await tronWeb.trx.getTransactionInfo(txID);
/*
 info 关键字段：
 - receipt.result: "SUCCESS" | "FAILED"        // 业务是否成功
 - receipt.energy_usage / energy_fee          // Energy 消耗与燃烧费用
 - receipt.bandwidth_usage / bandwidth_fee    // 带宽消耗
 - contractResult: [""] (空=成功) 或 revert 原因
 - log: [...]                                 // 合约事件日志（含 Transfer 等）
 - blockNumber / blockTimeStamp
*/
if (info.receipt && info.receipt.result === "SUCCESS") {
  console.log("成功！消耗 Energy:", info.receipt.energy_usage,
              "燃烧 TRX:", info.receipt.energy_fee / 1e6);
} else {
  console.log("失败原因:", info.receipt && info.receipt.result,
              "contractResult:", info.contractResult);
}
区分两层结果：广播返回的 result.result 只表示“交易被网络接受并打包”，不代表合约逻辑成功。真正的成败看 getTransactionInfo().receipt.result 与 contractResult。例如 USDT 余额不足时交易会“打包成功但 receipt=FAILED”。

16. 事件监听（TronGrid）

链上合约事件（如 Transfer）是钱包“发现入账”的主要手段。生产环境用 TronGrid 事件 API 轮询（或用 WebSocket 订阅）。

// demo7-event-watch.js —— 监听某地址收到的 USDT Transfer 事件
const TronWeb = require("tronweb");
const tronWeb = new TronWeb({ fullHost: "https://nile.trongrid.io" });

const USDT_CONTRACT = "TXLAQ63Xg1NAzckPwKHvzw7CSEmLMEqcdjmy";
const MY_ADDRESS_HEX = tronWeb.address.toHex("T你的地址");

async function pollTransfers(sinceTimestamp) {
  // 按合约 + 事件名查询历史事件
  const events = await tronWeb.getEventResult(USDT_CONTRACT, {
    eventName: "Transfer",
    since: sinceTimestamp,      // 从该时间戳（毫秒）起
    size: 50,                   // 每页数量
    page: 1,
    orderBy: "block_timestamp,asc",
  });
  for (const ev of events) {
    const to = ev.result.to;     // 接收方（hex）
    const value = Number(ev.result.value); // 最小单位
    if (to.toLowerCase() === MY_ADDRESS_HEX.toLowerCase()) {
      console.log("收到 USDT:", value / 1e6, "txID:", ev.transaction);
    }
  }
  return events.length;
}

// 每 10 秒轮询一次（生产可改为 Webhook/TronGrid 订阅）
let lastTs = Date.now() - 60 * 1000;
setInterval(async () => {
  try { lastTs = Date.now() - 60 * 1000; await pollTransfers(lastTs); }
  catch (e) { console.error("轮询出错", e.message); }
}, 10000);
安全点（重点，第 12 篇展开）：事件里的 contract_address 可能是伪造的假 USDT。监听时务必只相信白名单内的合约地址（如真正的 USDT 合约），并对 to 字段做精确匹配，否则会误把同名诈骗代币当作真实入账。

18. 离线签名与广播分离（冷钱包）

安全最佳实践：签名在离线/冷机器完成，广播在联网机器完成。两机不直接联网交换私钥。

// 18a-cold-sign.js —— 冷端：仅签名，不联网
const TronWeb = require("tronweb");
// 冷端只持有私钥，不配置 fullHost 也不广播
const cold = new TronWeb({ privateKey: "冷端私钥" });

async function coldSign(rawTx) {
  // rawTx 由热端构造后（不含签名）通过安全介质传入冷端
  const signed = await cold.trx.sign(rawTx, cold.defaultPrivateKey);
  return signed; // 把签名后的交易回传热端广播
}

// 18b-hot-build.js —— 热端：构造交易
const hot = new TronWeb({ fullHost: "https://nile.trongrid.io" });
async function buildTrx(to, amountTrx) {
  const tx = await hot.transactionBuilder.sendTrx(
    to, hot.toSun(amountTrx), hot.defaultAddress.base58
  );
  return tx; // 传给冷端签名
}

// 18c-hot-broadcast.js —— 热端：广播冷端签回的交易
async function broadcast(signedTx) {
  const ret = await hot.trx.broadcast(signedTx);
  console.log("广播:", ret);
}
多签冷签：若账户是多签（第 9 节），冷端可分别对每个 rawTx 用各自私钥 sign(tx, pk, 0xff /* permissionId */) 签名，热端用 broadcast 时 signature 数组里包含多个签名，协议层按权重校验。

19. 常见坑与排查清单

新手必踩的 5 个坑：
  1. feeLimit 设太低：合约交易不传 feeLimit 或传太小，直接失败。解决：send 时带 feeLimit: toSun(20~50)。
  2. 新地址未激活：往全新地址打 USDT 失败，因为地址不存在。解决：先转 1 TRX 激活。
  3. Energy 不足烧 TRX 超预期：没质押就调合约，单笔烧 ~3.8 TRX。解决：预质押 TRX 换 Energy，或租 Energy（第 12 篇）。
  4. 金额单位错：忘记 toSun/*10^6，把 1.5 TRX 当 1.5 SUN。解决：统一在构造前转换。
  5. 地址格式混用：把 T 开头地址直接塞进需要 hex 的 API。解决：用 tronWeb.address.toHex/fromHex 统一。
现象可能原因排查手段
广播返回 result=false参数非法/余额不足/地址未激活看 result.message（hex，解码为英文）
receipt=FAILED 但广播成功合约 revert（如余额不足、权限不足）查 contractResult、log
一直 timeout 未确认交易被卡（nonce/ref block 过期）重查 txID 状态，必要时重发
