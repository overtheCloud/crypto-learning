BTC 篇 III：生态与 BTCfi

从主链脚本走到 Layer2、资产协议与 BTC 质押。本篇不再重复基础概念，而是站在「钱包开发者」的视角，系统梳理比特币生态里你必须知道、且会直接影响钱包实现的技术栈。主要参考：Lightning BOLTs（github.com/lightning/bolts）、Liquid 文档（docs.liquid.net）、Stacks/Clarity（docs.stacks.co）、Ordinals（docs.ordinals.com）、Runes（github.com/ordinals/runes）、RGB（rgb.tech）、Babylon（babylonlabs.io）、BitVM（bitvm.org）。

本章目标：
  1. 说清闪电网络如何用「支付通道 + HTLC」把链下交易变成链上最终结算，并能用 Polar 在本地开一条通道。
  2. 区分 Liquid、Stacks、RGB 这三种「扩展路线」的本质差异：侧链、L2 结算层、客户端验证资产协议。
  3. 彻底理解 Ordinals / BRC-20 / Runes 三种资产范式的数据写入位置与 UTXO 模型影响，知道钱包为何要做「铭文感知」。
  4. 说清 Taproot（bc1p）地址在生态中的核心地位，并能在钱包里实现 cardinal 与 ordinal/taproot 双地址模式。
  5. 了解 Babylon 质押与 BitVM 这两个「把 BTC 安全属性外溢」的前沿方向，以及它们对钱包签名流程的潜在要求。

1. 总览：比特币生态的分层地图

读完前两篇，你已经能用 bitcoinjs-lib 在主链（L1）上收发比特币、写脚本、做多签与 PSBT。但「在 L1 上做一切」代价很高：区块空间稀缺、确认慢、无法跑复杂合约。于是生态自然按「离主链的距离」分成了几层。

层代表方案信任假设典型用途
L1 主链原生 BTC、Taproot比特币 PoW 全网最终结算、冷存储
状态通道闪电网络对手方在线 + 监控链上毫秒级小额支付
侧链Liquid、Rootstock联邦 / 合并挖矿 confidential 转账、代币
L2 结算层Stacks、Babylon锚定 BTC 经济安全sBTC、质押、合约
资产协议Ordinals、Runes、RGB协议共识（链下解释）NFT、FT、稳定币
计算层BitVM欺诈证明 + 挑战期乐观验证任意计算
一个关键认知：除了 L1 主链是比特币全网共识保证的，下面每一层都引入了额外的信任假设或新的「协议共识」。作为钱包开发者，你写的每一行与这些层交互的代码，本质都是在替用户相信某个外部系统。把信任边界写清楚，是钱包安全的第一课。

我们可以用一张「安全—性能」光谱来建立直觉：越靠近 L1，最终性越强、篡改成本越高，但吞吐越低、功能越受限；越往外，吞吐与表达力越强，但你需要额外假设「运营方诚实」「索引器一致」「挑战者存在」。没有银弹，只有权衡。

2. 闪电网络：链下支付通道

2.1 为什么需要闪电网络

比特币主链确认一笔交易通常需要 10 分钟到 1 小时，且每笔都要付手续费。用 L1 去买一杯咖啡：慢、贵、还暴露隐私。闪电网络的思路是：把绝大多数小额交易移到链下，只在「开通道」和「关通道」时上链，中间可以发生无限次近乎免费的即时转账。

2.2 支付通道：两个人之间的私人账本

假设 Alice 和 Bob 各拿出 0.5 BTC 放进一个 2-of-2 多签地址（通道资金），这笔「融资交易（funding tx）」必须上链锁定资金。之后他们在链下不断交换一笔「承诺交易（commitment tx）」，内容永远是「这个 2-of-2 池子里，Alice 占 X、Bob 占 Y」。只要 X+Y 恒等于 1，账本就是自洽的。

# 通道状态演进（链下，不上链，只有最新一版有效）
初始：Alice 0.5 / Bob 0.5
Alice 付 Bob 0.1：Alice 0.4 / Bob 0.6   # 新承诺交易，双方签名
Alice 付 Bob 0.2：Alice 0.2 / Bob 0.8   # 更新的承诺交易，使旧版作废
双花问题在链下重现：如果 Alice 把旧版承诺交易（她还占 0.5）偷偷上链，她就能「双花」掉已经付给 Bob 的钱。闪电网络用两种机制防止：①每更新一次状态就用一把新「撤销密钥（revocation key）」交给对方，旧状态的撤销密钥一旦被广播，对方可立刻罚没全部资金；②配合时间锁让对手方有时间反应。

2.3 承诺交易的「对称」结构

每次状态更新，双方其实各自持有一份镜像的承诺交易：A 持有的版本允许 A 立即取回自己的部分、但 B 的部分要等时间锁解锁（给 B 反应时间）；B 持有的版本反之。配合 revocation key，谁广播旧状态谁就被罚没。这种「不对称」是闪电安全的核心。

# A 持有的承诺交易（A 视角）
output0: <A 余额> 给 A，但带相对时间锁（CSV），让 B 有时间罚没
output1: <B 余额> 立即给 B
# 若 A 广播了旧状态，B 用 revocation key 取走 output0，A 颗粒无收

2.4 HTLC：把通道连成网络

只有两两通道还不够。要付给一个不直连的人，需要多跳路由。闪电网络用 HTLC（Hash TimeLock Contract，哈希时间锁合约）实现：

  • 收款方 Carol 生成一个秘密 preimage R，把哈希 H = hash(R) 放进发票（invoice）。
  • 付款方 Alice 沿路径 A→B→C 逐跳构造 HTLC：每一跳都「若提供 R 则付款，否则超时退款」。
  • Carol 揭示 R 取走最后一跳的钱，R 沿原路回传，每一跳依次解锁。任一段超时则整条回滚。
# HTLC 的语义（伪脚本）
IF
  <H>  # 要求支付方提供 R 使得 hash(R) == H
  SHA256
  EQUAL
  <Carol 公钥> CHECKSIG
ELSE
  <超时高度/时间> CHECKLOCKTIMEVERIFY
  DROP
  <Alice 公钥> CHECKSIG
ENDIF

2.5 路由费与流动性

中间节点 B 帮忙转发要收「路由费」：通常是 base_fee + fee_rate * amount。通道是有方向的——A→B 有 0.4 流动性不代表 B→A 有。钱包做支付时，路由算法要在「图」里找到一条各段出向流动性都足够的路径，否则支付失败。这是闪电钱包 UX 最难的部分之一。

2.6 发票 BOLT11 与节点软件

闪电支付靠的是发票（invoice）而非地址。BOLT11 发票是一串 bech32 编码，内含收款节点 ID、金额、支付哈希、过期时间、路由提示等。常见节点实现：

软件语言特点
LNDGo生态最成熟，Lang 接口友好
Core Lightning (CLN)C轻量、插件化
EclairScala移动端、ACINQ 维护
钱包视角：把闪电网络接入钱包有两种模式——①自己做完整节点（LND/CLN，需要常在线、备份 channel.db 与静态通道备份 SCB）；②用托管钱包或非托管但远端节点（如 LDK 嵌入式、或连接自家节点）。托管意味着你把通道私钥交给了服务商，这是信任权衡，必须在 UI 中说清楚。

2.7 用 Node.js 读 LND 余额（gRPC 示例）

如果钱包后端直连 LND，最干净的方式是用它的 gRPC/REST 接口。下面给出一个用 Node.js 读通道余额的最小示意（真实项目请用官方 lnd npm 包或 REST）：

// 仅示意：通过 LND REST 读取通道与钱包余额
// 需要先生成 macaroon 与 tls.cert，并在请求头带上 macaroon
const https = require("https");
const fs = require("fs");

const macaroon = fs.readFileSync("/path/to/admin.macaroon").toString("hex");
const options = {
  hostname: "127.0.0.1",
  port: 8080,
  path: "/v1/balance/channels",
  method: "GET",
  headers: { "Grpc-Metadata-macaroon": macaroon },
  ca: fs.readFileSync("/path/to/tls.cert"),
};

https.get(options, (res) => {
  let body = "";
  res.on("data", (c) => (body += c));
  res.on("end", () => {
    const bal = JSON.parse(body);
    console.log("通道可发送(msat):", bal.balance);
    console.log("待结算(msat):", bal.pending_open_balance);
  });
});

2.8 洋葱路由与监听塔（Watchtower）

闪电支付的路径信息是逐跳加密的（洋葱路由 Sphinx）：每个节点只能看到「上一跳和下一跳」，看不到完整路径，保护隐私。另一项关键工程是监听塔：用户把「如果对手方广播旧状态，请用这个 revocation key 罚没」的证据外包给第三方塔，自己离线时塔代为监控链上，避免被双花。

// 监听塔交互概念（示意）
// 1) 用户本地计算 revoked state 的 justice tx（罚没交易）
// 2) 加密后发给 watchtower，附带触发条件（某 txid 上链）
// 3) 塔监视链；命中条件则广播 justice tx
// 钱包需让用户可选择自建塔或可信塔，并说明「塔可看到你有哪些通道」

2.9 用 JS 模拟一次 HTLC 结算

下面用不到 30 行伪代码展示「R 揭示后资金如何解锁」，帮助建立直觉：

// HTLC 结算模拟（教学用，非真实密码学）
function htlcClaim(secretR, preimageHash, expectedHash, toCarol, toAlice) {
  const h = sha256(secretR);
  if (h === preimageHash && h === expectedHash) {
    return toCarol;            // 提供正确 R，Carol 取走
  }
  if (Date.now() > timeout) {
    return toAlice;            // 超时，Alice 退款
  }
  throw new Error("等待 R 或超时");
}
// 真实实现里 R 的验证发生在比特币 Script，非应用层

3. 闪电网络实战：Polar 开通道

Polar（github.com/jamaljsr/polar）是一个本地可视化的闪电网络模拟器，能一键起多个 Bitcoin Core（regtest）+ LND/CLN 节点，非常适合练手。下面是一套最小可跑流程。

3.1 图形界面步骤

  1. 新建网络，添加 1 个 bitcoind(regtest) + 2 个 LND 节点（alice、bob）。
  2. 启动网络，等待 bitcoind 出块（Polar 可一键「mine a block」）。
  3. 给 alice、bob 各发送 regtest 币（Polar 的「Deposit」按钮，它会自动挖块确认）。
  4. 在 alice 节点点「Create Channel」，选择 bob 为目标，容量（capacity）设 1,000,000 sat，push 500,000 sat 给 bob。
  5. 等待通道上链确认，状态变为 Active。

3.2 用 LND 命令行（lncli）复刻

# 假设 alice 的 lncli 通过 --network regtest --lnddir 指向其数据目录
# 1) 给 bob 的节点 ID 建立连接（peer 由 Polar 在节点详情页给出）
lncli connect <bob_pubkey>@<bob_host>:<port>

# 2) 开通通道：容量 1,000,000 sat，其中 500,000 推给 bob
lncli openchannel --node_key=<bob_pubkey> --local_amt=1000000 --push_amt=500000

# 3) 让 bitcoind 挖 6 个块使通道确认
# （在 Polar 里点 mine blocks，或用 bitcoin-cli generatetoaddress）

# 4) 查看通道
lncli listchannels

# 5) bob 生成一张收 10 sat 的发票
# （切到 bob 的 lncli）
lncli addinvoice --amt=10

# 6) alice 凭发票付款
lncli payinvoice <bolt11_invoice>

# 7) 查询余额变化
lncli channelbalance
lncli walletbalance

3.3 通道的生命周期与关闭

通道不止「开」一种结局：

关闭方式触发特点
合作关闭双方同意单笔结算交易，立即生效，省费
单方关闭一方广播承诺交易对手方需等待时间锁才能取回资金
罚没关闭广播了 revoked 旧状态对手方用 revocation key 取走全部
钱包必须做的：① 定期备份通道状态（SCB 或完整 db）；② 节点离线太久可能错过对手方广播的旧状态，需在 UI 提示「长期离线风险」；③ 关通道时要向用户解释「资金回到主链需要等待确认」。
练习：在 Polar 里构造一条 A→B→C 三跳支付：再加一个 carol 节点，让 alice 通过 bob 路由付给 carol。观察 lncli listchannels 中每条通道的本地/远端余额如何因 HTLC 临时变化。

4. Liquid 侧链与 confidential 资产

4.1 什么是侧链

Liquid 是由联邦（federation）运营的、与比特币双向锚定的侧链。用户把 BTC 锁在主链上的 federation 多签地址，联邦在 Liquid 上发行等量的 L-BTC；赎回时反向销毁。侧链有自己独立的区块、地址格式（以 lq1 / V / G 等开头）和更短的确认时间（约 1 分钟）。

信任模型：Liquid 的安全不来自比特币矿工，而来自运营联邦的成员（多为交易所、基础设施公司）。联邦作恶或合谋可冻结/盗取资金。它换来的是：更快的区块、更强的隐私（confidential transactions 隐藏金额与资产类型）、以及原生的发行资产（issuance）能力。

4.2 Confidential Transactions（机密交易）

Liquid 用 Pedersen 承诺 + 范围证明（Bulletproofs）隐藏每笔交易的金额和资产类型，同时仍能通过密码学证明「输入总额 = 输出总额」不超发。对钱包开发者而言，这意味着你的 UI 不能像主链那样直接显示从链上「读出」的余额，而必须依赖钱包本地维护的 blinded 视图。

// 概念示意：confidential 输出不再直接写金额，而是写承诺
// vout[i].value = "00" (占位) + range_proof
// vout[i].asset = 资产承诺 (隐藏是 L-BTC 还是某发行代币)
// 验证者能确认 sum(inputs) == sum(outputs) 而不知具体数字

4.3 资产发行（Issuance）

Liquid 允许任意人在侧链上发行带「资产标签」的代币（用于稳定币、证券型代币等）。发行时会产生一个重铸令牌（reissuance token），持有它才能增发/销毁。钱包若要展示 L-BTC 之外的资产，需要解析 issue 交易并维护资产注册表。

# elements-cli（Liquid 的 bitcoind 改版）发行资产示意
# 在 Liquid 节点上发行 100 万单位的「MyAsset」
elements-cli issueasset 1000000 0
# 返回包含 asset 标识与 reissuance token 的 JSON
# 钱包需保存 asset 的 hex 标签以便后续转账展示

4.4 钱包整合要点

  • 地址格式不同：Liquid 使用自己的 bech32 变体与前缀，不能和主链地址混用，否则资金丢失。
  • 余额来自盲化：本地必须保存 blinding key，丢了就看不到/花不了自己的 confidential 余额。
  • 区块更快：约 1 分钟出块，确认数语义与主链不同，UI 文案要区分。

4.5 双向锚定：peg-in 与 peg-out

用户要进入 Liquid，需要先 peg-in（主链锁 BTC → 侧链发 L-BTC）；退出则 peg-out（销毁 L-BTC → 主链解锁 BTC）。前者由用户发起、联邦确认；后者需联邦多签协作。钱包必须清晰区分「我在主链上的 BTC」与「我在 Liquid 上的 L-BTC」，二者地址与私钥体系不同。

步骤peg-in（入金）peg-out（出金）
1在 Liquid 生成领取地址在主链生成收款地址
2主链向 federation 多签发 BTC侧链发起 burn L-BTC
3联邦确认后侧链 mint L-BTC联邦多签在主链解锁 BTC
信任点联邦诚实 mint联邦诚实签名释放

5. Stacks：BTC 锚定的智能合约 L2

5.1 PoX 与锚定

Stacks 是一条独立的 L2 区块链，它的出块哈希会写到比特币区块里（锚定），从而继承 BTC 的安全性叙事。其共识叫 PoX（Proof of Transfer）：矿工不烧电，而是把 BTC 转给 STX 持有者（「堆叠者」）来竞争出块权。这样 BTC 持有者可以通过「锁定 STX 换 BTC 奖励」参与，而不消耗额外能源。

5.2 Clarity：可预测的智能合约语言

Stacks 的合约语言 Clarity 刻意不是图灵完备的：没有循环、所有函数必须能静态判定是否终止。它直接以源码形式上链（不编译成字节码），所以任何人看到的合约就是实际执行的合约，消除「编译不一致」风险。变量用显式 let，状态用 map / var 存储。

;; Clarity 合约示例：一个简单的计数器
;; 部署在 Stacks 上，可用 Hiro Explorer 查询
(define-data-var counter int 0)

(define-public (increment)
  (begin
    (var-set counter (+ (var-get counter) 1))
    (ok (var-get counter))))

(define-read-only (get-count)
  (var-get counter))

;; 调用：在 Clarinet 或 Hiro 钱包里执行 (increment)
;; 返回新计数；任何人可 (get-count) 读取当前值

5.3 Clarity 的类型与权限

Clarity 是强类型的，常见类型有 uint、principal（地址）、bool、(response ...)、(optional ...) 等。写合约要用 define-public 返回 (ok ...) 或 (err ...)。钱包在调用合约前，应当先用节点的 read-only 模拟执行，向用户展示「会调用哪个函数、可能失败的错误码」。

;; 一个带权限检查的代币转账片段（示意）
(define-map balances principal uint)

(define-public (transfer (to principal) (amt uint))
  (let ((sender tx-sender)
        (bal (default-to u0 (map-get? balances sender))))
    (asserts! (>= bal amt) (err u1))           ;; 余额不足
    (map-set balances sender (- bal amt))
    (map-set balances to (+ (default-to u0 (map-get? balances to)) amt))
    (ok true)))
注意转义：上面的 >= 在 HTML 代码块里必须写成 &gt;=，否则浏览器会把 > 当成标签结尾。所有 < > & 在 <pre><code> 内都要转义。

5.4 sBTC：把 BTC 真正搬上 L2

sBTC 是 Stacks 上的 BTC 锚定资产（由去中心化签名者网络托管主链 BTC，1:1 发行 sBTC）。有了 sBTC，开发者可以在 Clarity 合约里写「用 BTC 做抵押借贷、DEX、收益策略」的 BTCfi 应用，而底层安全锚定回比特币。钱包若要支持 sBTC，需要同时管理主链 BTC 地址、Stacks 地址（SM... 格式）和桥接存款/赎回流程。

// sBTC 存款/赎回流程（概念）
// 1) 用户从主链 BTC 地址向 sBTC 桥接多签地址发送 BTC（带 Stacks 地址 memo）
// 2) 签名者观察到主链存款，在 Stacks 上调用 mint，给用户 SM 地址发 sBTC
// 3) 赎回时用户在 Stacks 烧毁 sBTC，签名者将主链 BTC 退回用户 BTC 地址
// 钱包需展示：主链确认数、桥接状态、预计等待时间
本地开发：用 clarinet（Stacks 官方 CLI）新建项目、写合约、起本地测试网；用 Hiro Wallet 浏览器扩展连接 dApp 做交互测试。建议钱包在展示 sBTC 余额时明确标注「由签名者托管，非主链 BTC」。

5.5 钱包如何处理 Stacks 地址与资产

Stacks 地址以 SM（主网）/ SN（测试网）开头，与比特币地址体系无关，但常用同一套助记词（BIP39）按不同派生路径生成。钱包要同时管理三类东西：

  • 主链 BTC 地址：用于 peg-in 锁仓。
  • Stacks 地址（SM...）：用于 STX、sBTC、合约调用。
  • 资产状态：sBTC 余额、合约内部状态由 Stacks 节点/API 提供。
// 概念：从同一助记词派生两套地址
// BTC（BIP84）:  m/84'/0'/0'/0/0  -> bc1q...
// STX（Stacks 路径）: 对应 Stacks 派生 -> SM...
// 钱包应把二者关联展示，并提示「向 SM 地址误发 BTC 会丢失」

6. Ordinals 与 Inscriptions（铭文）

6.1 Satoshi 编号

Ordinals 协议给每一个聪（satoshi，1 BTC = 1 亿聪）按顺序编号。编号规则：按挖出的顺序，第 N 个被挖出的聪获得编号 N。编号可以通过算法从「它在哪个区块、区块内第几个输出、输出内第几个聪」反推出来。这样每个聪都变成了一个可单独追踪的「藏品」。

6.2 铭文（Inscription）如何刻进链上

铭文把任意数据（图片、文本、代码）写入比特币交易。关键技术点：

  • 数据放在隔离见证（witness）里，因为 witness 数据享受 1/4 的区块权重折扣，便宜。
  • 用 OP_FALSE OP_IF ... OP_ENDIF 包裹一段「envelope」，里面是 ContentType 与数据分片（OP_PUSH）。
  • 铭文必须花在一个 Taproot 输出上（利用其 witness 可编程性），所以该输出地址是 bc1p...。
# 一个铭文交易的脚本结构（示意，实际由 ord 组装）
witness:
  <空>                       # 隔离见证第一个元素（兼容）
  OP_FALSE
  OP_IF
    OP_PUSH "ord"            # 协议标识
    OP_PUSH 1                # 内容类型标签 = 1
    OP_PUSH "text/plain;charset=utf-8"
    OP_PUSH 1                # 数据标签
    OP_PUSH <数据分片1>
    OP_PUSH <数据分片2>
    ...
  OP_ENDIF
  <Taproot 脚本花费见证>       # 用该 bc1p 输出的私钥签名花费

6.3 提交-揭示两阶段（commit-reveal）

刻铭文实际是两笔交易：commit 把铭文内容的哈希（作为 Taproot 脚本叶）上链锁定；reveal 在后续块里花掉 commit 输出，把真实数据放出来。两笔必须分开（不能同块），否则数据未确认就被引用会失败。钱包/工具要管理这种「待 reveal」的中间状态。

阶段上链内容用户感知
commit仅哈希承诺（小）已付一半费，铭文未可见
reveal真实 witness 数据铭文正式出现在浏览器

6.4 用 JS 估算铭文体积与手续费

钱包在帮用户刻铭文前，应预估这笔交易的体积，避免手续费误算。下面是一个粗略估算示意：

// 估算铭文交易 vsize（仅示意，真实用 bitcoinjs 构建后再算）
function estimateInscriptionVSize(dataBytes) {
  // witness 数据享受 1/4 权重，但 envelope 有固定开销
  const envelopeOverhead = 40;       // OP_FALSE/IF/内容类型标签等
  const witnessWeight = (envelopeOverhead + dataBytes) * 4; // 转为 weight
  const baseVSize = 110;             // 典型 taproot 输入的基准 vsize
  const vsize = baseVSize + Math.ceil(witnessWeight / 4);
  return vsize;
}
// 若数据 100 KB，vsize 约 25k+ vB，按 20 sat/vB 需约 500k sat 手续费！
console.log(estimateInscriptionVSize(100 * 1024));
钱包的重大影响：一个被刻了铭文的 UTXO，其「聪」具有收藏价值，若被当作普通找零花掉，会在无意中把藏品送给矿工或混进普通资金（叫「铭文被损毁/转移」）。钱包必须能识别哪些 UTXO 含有铭文，并允许用户锁定（freeze）它们，避免误花。

6.5 Sat 的稀有度（rarity）

Ordinals 圈子里给 sat 定义了「稀有度」，因为编号算法让某些 sat 特别稀缺，从而更值钱。常见等级：

等级定义数量
common普通，每个区块内非第一个约 2.1 亿亿
uncommon每个区块的第一个 sat约 693 万（按减半算）
rare难度调整期的第一个 sat约 3432
epic减半事件后的第一个 sat32
legendary创世块后的第一个 sat1（sat 0）
mythic创世 sat（sat 0）本身1
钱包意义：如果你要展示「这个 sat 稀有」，需要用算法根据区块高度反查它的稀有度属性。注意稀有度是社区共识，不影响链上可转移性，钱包标注时要避免让用户误以为「稀有=更有用」。

7. BRC-20 与 Runes：UTXO 上的同质化代币

7.1 BRC-20：用 JSON 铭文当账本

BRC-20 是 2023 年出现的实验性同质化代币标准。它不改动比特币协议，而是约定：把 deploy / mint / transfer 三种操作的 JSON 文本各自刻成铭文，再靠链下索引器（indexer）按时间顺序重放这些铭文，算出每个地址的余额。

// BRC-20 的 deploy 铭文内容示例（刻进 witness 的纯文本 JSON）
{
  "p": "brc-20",
  "op": "deploy",
  "tick": "ordi",
  "max": "21000000",
  "lim": "1000"
}
// mint 铭文：{"p":"brc-20","op":"mint","tick":"ordi","amt":"1000"}
// 余额完全由索引器主观解释，不同索引器可能结论不同！

7.2 BRC-20 的转移两步走

BRC-20 转移很别扭：先刻一张 transfer 铭文「授权转移 X 个 tick」，再另外发起一笔普通 BTC 交易把承载该铭文的 UTXO 发给接收方。也就是说「代币」和「承载它的 UTXO」是绑定的——花掉那个 UTXO 就等于发送了代币。这正是它产生大量垃圾 UTXO 的原因。

7.3 Runes：UTXO 原生的同质化代币

Runes（由 Ordinals 创始人 Casey Rodarmor 提出）批评 BRC-20 产生了大量「废 UTXO」污染。Runes 把代币余额直接编码进 UTXO 的脚本/OP_RETURN，每个 UTXO 携带「这个 UTXO 属于哪个 rune、多少量」的状态，转移时按 UTXO 模型自然流转，更贴合比特币原生范式。

# Runes 交易输出携带状态（概念）
# 输出0: RUNE 转移：{ rune_id: X, amount: 1000 }  -> 给接收方
# 输出1: RUNE 转移：{ rune_id: X, amount: 500 }   -> 找零回自己
# 若某输入有 rune 但输出未分配，则按协议「销毁或归矿工」
# 这与 UTXO 模型天然契合：花输入=重分配其 rune 余额

7.4 对比表与钱包含义

维度BRC-20Runes
数据载体witness 铭文（JSON 文本）OP_RETURN / 输出脚本
状态存储链下索引器重放UTXO 携带余额状态
UTXO 影响大量垃圾 UTXO尽量复用、减少残留
依赖需要 BRC-20 索引器Runes 索引器（但模型更干净）
转移机制transfer 铭文 + 后续 sendUTXO 花费即转移
共识是「社会性的」：Ordinals、BRC-20、Runes 都不是比特币协议层强制的。它们的有效性来自「足够多人运行同一个索引器规则」。钱包若要展示这些资产，必须接入对应索引器（如 ord、ordsupply、官方 API），并明确告知用户这是第三方解释、可能与其他钱包显示不一致。

7.5 用 JS 解析 BRC-20 transfer 铭文

钱包接入 BRC-20 时，需要从索引器拉取该地址相关的铭文，并按协议解析。下面是一个解析 transfer 文本的极小示例：

// 解析 BRC-20 transfer 铭文文本（示意，生产请用成熟索引器 SDK）
function parseBrc20(text) {
  let o;
  try { o = JSON.parse(text); } catch { return null; }
  if (o.p !== "brc-20") return null;
  switch (o.op) {
    case "deploy": return { type: "deploy", tick: o.tick, max: o.max, lim: o.lim };
    case "mint":   return { type: "mint",   tick: o.tick, amt: o.amt };
    case "transfer":return { type: "transfer", tick: o.tick, amt: o.amt };
    default: return null;
  }
}
// 注意：余额 = 所有有效 mint/transfer 的净流入，规则由索引器定义

7.6 Runes 的 edict（法令）模型

Runes 在交易输出里用一串 edict 描述「把哪个 rune 的多少量分给第几个输出」。钱包构造 Runes 转移时，要正确填写 edict 数组，并保证所有输入 rune 都被分配（未分配的按协议处理）。这是比 BRC-20 更贴近 UTXO 的范式，但构造逻辑也更易出错。

# Runes edict 示意（每个 edict = id, amount, output_index）
edicts = [
  { rune_id: 1, amount: 1000, output: 0 },  # 给接收方输出
  { rune_id: 1, amount: 500,  output: 1 },  # 自己找零输出
]
# 若输入共 1500，分配 1500，无剩余
# 若只分配 1000，剩余 500 按协议可能销毁或归矿工

8. RGB：客户端验证的智能资产

RGB 走了一条和 Ordinals 完全不同的路：客户端验证（client-side validation）。它把资产的定义、转移历史全部放在链下，比特币链上只承担「一次性的承诺（commitment）」——把一段哈希通过 Taproot 输出或 OP_RETURN 写进交易，作为「这笔链下状态已更新」的锚点。

  • 发行方定义合约（资产总量、名称、模式），生成初始状态。
  • 每次转移，接收方收到「历史证明包」，本地验证整条链是否合法（双花、超发）。
  • 链上交易仅做一次 Pedersen 承诺，不泄露资产细节，也不占用 Blob 数据。
// 概念：RGB 把状态承诺藏进 taproot 输出的 tweak
// 链上只看得到：一个 Taproot 输出，其脚本/内部密钥被 tweak 过
// 真正的数据在接收方本地：
//   - schema（合约规则）
//   - genesis（发行）
//   - transition（每次转移的状态 diff）
// 钱包需要配套 RGB 节点 / 轻客户端来收发这些 "stash"

8.1 单-use-seal：UTXO 即「锁」

RGB 用一个巧妙原语叫 single-use-seal：把比特币的 UTXO 当作「封条」。要转移资产，必须花费那个承载旧状态的 UTXO（封条被撕开=旧状态作废），并在新 UTXO 上盖新封条（新承诺）。因为 UTXO 只能花一次，双花在链层面被物理禁止，而详细历史只在持有者之间传递。

钱包含义：RGB 资产不会出现在比特币余额里，也不在 BTC 区块浏览器可查。钱包必须实现一套独立的状态数据库来存储和验证 RGB stash，并在花费承载承诺的 UTXO 时保持该 UTXO 不被破坏（否则链下状态锚点丢失）。

9. Babylon：BTC 原生质押

Babylon 的目标是把比特币的安全（经济权重）借给其他 PoS 链：BTC 持有者在比特币主链上做一笔自带时间锁的自我托管质押交易，把「slashable 凭证」锚定给某条 PoS 链；若该 PoS 链作恶，质押的 BTC 会被罚没（通过可提取的时间锁 + 密码学证据）。

  • 不跨链桥接：BTC 始终留在主链，不发行包装币，保持自托管。
  • 快速解质押：利用比特币时间锁实现「解质押后经过 N 个区块才能动用」，期间若被证明作恶则罚没。
  • 对钱包的影响：需要构造带 CLTV/CSV 时间锁的输出（第二篇学过），并引导用户理解「质押期间资金不可动用」。
// 质押输出示意：资金锁定到时间 T，且只有用户公钥 + 满足罚没条件可花
IF
  <罚没证据验证脚本>   # 由 Babylon 协议定义
ELSE
  <T> CHECKLOCKTIMEVERIFY
  DROP
  <用户公钥> CHECKSIG
ENDIF

9.1 钱包签名流程的变化

普通转账用户只关心「金额对、地址对」。但 Babylon 质押要求用户在自己的 UTXO 上附加时间锁脚本，并且可能要在「罚没挑战窗口」内保持可响应。钱包需要：

步骤用户动作钱包职责
创建质押选金额、锁定时长构造带 CLTV 的输出，展示锁定截止高度
等待无需操作监控罚没事件，报警
解质押发起解除提示「T 个块后才能动用」

9.2 加密 covenant 与「可提取时间锁」

Babylon 的罚没依赖一种可提取时间锁（extractable one-time timelock, EOTS）：质押者用特殊密钥签名，一旦同一密钥签了「两份冲突的 PoS 区块」，就能从签名中反解出私钥，从而动用质押输出实施罚没。钱包在生成这种签名时必须非常小心——绝不能让同一 EOTS 密钥签两份消息，否则资金自动暴露。

// 概念：EOTS 签名 = 普通 BIP340 签名 + 可被提取的 nonce
// 正用：签一份 PoS 投票 -> 正常
// 滥用：用同一 nonce 签两份冲突投票 -> 私钥被提取 -> 罚没
// 钱包应将 EOTS 密钥隔离，禁止复用 nonce

10. BitVM：比特币上的乐观计算

BitVM（BitVM 1 / BitVM 2）试图在不大改比特币脚本的前提下，让链上能验证「任意计算」是否正确——采用乐观 Rollup 思路：

  • 把程序编译成巨大的布尔电路（NAND 门网），预上链承诺。
  • 默认相信计算者提交的结果；若有人质疑，发起欺诈证明挑战，双方通过少量链上交互逐步逼出错误门。
  • 只要有一个诚实挑战者，作弊必被抓住并罚没。

10.1 为什么用 NAND

NAND 门是「通用」的：任何布尔电路都能只用 NAND 表达。BitVM 把所有计算归约成 NAND 门的组合，再设计一套「承诺每个门输出 → 挑战者逼问某一门 → 链上只验证那一门」的协议，把验证成本从「重跑整个程序」降到「验证一条路径」。

# 乐观验证流程图（概念）
# 1) Prover 在链上承诺电路 + 声明输出 Y
# 2) 静置挑战期；若无人质疑，Y 被接受
# 3) 若有 Challenger 质疑：
#     双方交互式逼问：门 g1, g2, ..., gk 的真值
#     对某一门的矛盾在链上用 Script 验证
# 4) 作弊者被罚没，诚实方获奖励
争议与现状：BitVM 理论上能带来图灵完备的 BTC 计算，但当前（截至本教程撰写时）仍处早期：电路规模巨大、挑战和交互成本高、尚未有大规模生产部署。钱包开发者应关注其签名交互协议（用户可能需要在承诺/挑战窗口内做特定签名），但不必现在就接入。把它当作「比特币可编程性演进的方向」来理解即可。

11. 钱包开发者须知：bc1p 与铭文感知

读完本篇，落到工程上，钱包要实现「生态友好」，至少要处理以下三件事。

11.1 支持 Taproot 地址 bc1p

Taproot（bc1p...，Bech32m 编码）既是 Ordinals 铭文的载体，也是最好的隐私与多签形态。钱包必须能生成和解析 bc1p：

const bitcoin = require("bitcoinjs-lib");
const { ECPairFactory } = require("bitcoinjs-lib");
const tinysecp = require("tiny-secp256k1");
bitcoin.initEccLib(tinysecp);
const ECPair = ECPairFactory(tinysecp);

// 生成 x-only 公钥的 Taproot 地址（用于接收可铭文的资金）
const keyPair = ECPair.makeRandom({ network: bitcoin.networks.bitcoin });
const { address, output } = bitcoin.payments.p2tr({
  internalPubkey: keyPair.publicKey.slice(1), // 去掉前缀字节，取 x-only
  network: bitcoin.networks.bitcoin,
});
console.log("bc1p 地址:", address);
// 注意：Bech32m（不是 Bech32）才是 Taproot 的正确编码，必须校验

11.2 铭文感知的 UTXO 管理

普通钱包把「所有未花费输出」视为同质化余额。但含铭文/Rune 的 UTXO 是非同质化的。必须：

  • 查询索引器，标记哪些 UTXO 含铭文、哪些含 rune。
  • 在 coin selection 时默认排除这些 UTXO，或提供「锁定」开关。
  • 若用户执意花费，UI 必须弹强警告：「此操作会转移/损毁其中的铭文」。

11.3 双地址模式：cardinal 与 ordinal/taproot

最佳实践是把资金分成两类地址：

地址类型用途建议
cardinal（bc1q 等）日常收付款、找零默认地址
ordinal / taproot（bc1p）接收、保管铭文与 Runes单独标签，不自动用于找零
// 双地址模式：生成两种接收地址
function deriveAddresses(xpub, index, network) {
  // cardinal：BIP84 P2WPKH
  const cardinal = bitcoin.payments.p2wpkh({
    pubkey: bip84.derivePath(`0/${index}`).publicKey, network });
  // ordinal：BIP86 P2TR（x-only）
  const ordinal = bitcoin.payments.p2tr({
    internalPubkey: bip86.derivePath(`0/${index}`).publicKey.slice(1), network });
  return { cardinal: cardinal.address, ordinal: ordinal.address };
}

11.4 coin selection 改造示例

把「铭文感知」落到代码，最直接的是在选币时加一个过滤：

// 选币时排除含铭文的 UTXO（示意）
function selectCoins(utxos, targetSat, opts = {}) {
  const candidates = utxos.filter((u) => {
    if (opts.excludeInscribed && u.inscription) return false; // 含铭文则跳过
    if (opts.excludeRunes && u.rune) return false;             // 含 rune 则跳过
    return true;
  });
  // 贪心：先选最小能凑够的（或按手续费最优）
  candidates.sort((a, b) => a.value - b.value);
  let sum = 0, picked = [];
  for (const u of candidates) {
    picked.push(u); sum += u.value;
    if (sum >= targetSat) break;
  }
  return { picked, change: sum - targetSat };
}
工程清单：① 接入 ord / mempool 索引器获取铭文标注；② coin selection 增加 excludeInscription 参数；③ 对含 rune 的 UTXO 同理处理；④ 在所有「发送」界面做铭文转移警告；⑤ 备份时一并导出 ordinal 私钥路径（BIP86）。

11.5 用输出描述符表达 Taproot 收款

第二篇学过的 descriptors 在这里直接可用。一个支持 ordinals 的钱包，可以给每个 ordinal 地址配一条 tr(...) 描述符，便于用 Bitcoin Core 的 importdescriptors 建立 watch-only 视图并追踪铭文 UTXO：

# 单密钥 Taproot 描述符（BIP86，x-only 内部公钥）
tr([fp/86h/0h/0h]tpub.../0/*)#cs

# 带脚本叶（如 CSV 时间锁）的 Taproot（用于高级铭文逻辑）
tr(KEY,leaf_a)

# 钱包导出时应同时给出 descriptor 与 checksum，便于在其他 Core 节点恢复

11.6 铭文 UTXO 的「不要动」策略

除了在 coin selection 排除，钱包还应在数据库层给 UTXO 打标签，并在任何「最大金额发送」「清空钱包」类操作里自动跳过它们。一个稳妥的存储结构：

// UTXO 元数据示例（钱包本地存储）
{
  txid: "abc...", vout: 0, value: 12000,
  inscription: { id: "abc...i0", content_type: "image/png", sat: 1900000000 },
  rune: null,
  frozen: true          // 默认冻结，需用户显式解冻
}
// 发送界面：frozen=true 的 UTXO 不进入预览，除非用户勾选「包含铭文」

12. 实战：用 ord 在 testnet 刻铭文

ord 是 Ordinals 官方命令行（github.com/ordinals/ord）。下面在 testnet 完整走一遍「刻一张图」的流程（主网同理，只是网络参数和真金白银的区别）。

12.1 环境准备

# 安装 ord（需先装 Rust 工具链）
cargo install ord

# 准备一个 Bitcoin Core testnet 节点（或 signet），ord 通过 RPC 交互
# bitcoin.conf 至少包含：
#   rpcuser=xxx
#   rpcpassword=yyy
#   testnet=1
#   server=1
#   txindex=1   # 推荐开启，便于索引

12.2 生成 Taproot 钱包并同步

# 让 ord 创建/使用自己的钱包（也可指定 --wallet 名）
ord --cookie-file=<path> -r <rpcurl> wallet create

# 查看接收地址（必须是 bc1p 才能刻铭文）
ord wallet receive

# 向该 bc1p 地址转入 testnet 币（从测试网水龙头或本地节点 sendtoaddress）
# 等待确认后同步
ord wallet balance

12.3 刻铭文并广播

# 把一段文本（或图片文件）刻成铭文
# 方式一：直接传文件
ord wallet inscribe <my-image.png>

# 方式二：文本
echo "hello bitcoin ecosystem" > note.txt
ord wallet inscribe note.txt

# ord 会构造：① _commit 交易（承诺）+ ② _reveal 交易（揭示数据）
# 自动广播并输出 inscription id，如：<txid>i0
# 用以下命令查看
ord wallet inscriptions

12.4 在钱包里验证铭文 UTXO 状态

刻完后，可以用 Bitcoin Core RPC 看该 inscription 落在哪个 UTXO 上，并确认它带了 witness 数据：

# 在 Bitcoin Core 侧查看 reveal 交易的 witness
bitcoin-cli getrawtransaction <reveal_txid> true
# 观察 vin[0].txinwitness 里是否含 "ord" / 数据分片

# 用 ord 自身解析
ord decode <reveal_txid>
练习：刻完后在 mempool.space 的 testnet 浏览器里搜索你的 inscription id，确认 witness 数据可见。再用本篇 11.3 的双地址代码，验证该 inscription 所在的 UTXO 若被普通转账花费会发生什么。

13.1 通用安全原则

  • 最小暴露：默认只用主链自托管，生态功能做成可关闭的「高级模式」。
  • 明确标注：每个非 BTC 余额都注明「由谁托管/由谁解释」。
  • 不可逆提醒：铭文转移、质押锁定都是不可逆或高成本操作，必须二次确认。
  • 备份完整：生态私钥、stash、通道 db、blinding key 都要纳入备份流程。

15. 本章小结与下一步

本篇我们把视野从「主链脚本」扩展到了整个比特币生态。请确认你能独立回答以下问题，再进入下一篇：

  • 闪电网络用哪两个核心机制（通道 + HTLC）把链下支付「锚定」回链上最终性？
  • Liquid、Stacks、RGB 三者的信任模型分别建立在什么之上？
  • Ordinals 把数据写进交易的哪一部分？为什么必须用 Taproot（bc1p）地址？
  • 为什么说 BRC-20 是「索引器共识」而非「协议共识」？这对钱包展示意味着什么？
  • Runes 相比 BRC-20 在 UTXO 模型上有什么改进？
  • 钱包做「铭文感知」需要哪三步（标注 / 排除 / 警告）？
  • Babylon 质押为何要求用户理解「时间锁期内资金不可动用」？
  • BitVM 用的是哪种验证思路（乐观 + 欺诈证明），它当前处于什么阶段？
工程落地最小集：
  • 支持 bc1p（BIP86）地址生成与解析。
  • 接入至少一个索引器，标注 inscription / rune UTXO。
  • coin selection 默认排除被标注的 UTXO，并提供冻结开关。
  • 对所有生态资产在 UI 标注信任来源与风险等级。
  • 把闪电、侧链、L2 的私钥/状态纳入统一备份流程。
一句话收尾：比特币生态的繁荣，本质上是「在不变的主链上，叠加可变的信任层」。你作为钱包开发者，扮演的正是「信任翻译器」——把每一层复杂的信任假设，翻译成用户能看懂、能控制的选择。
通往以太坊：下一篇我们将离开比特币的 UTXO 世界，进入账户模型（Account Model）与 EVM 智能合约生态。你会发现很多「比特币生态想做而受限」的事，在以太坊上用合约天然可做——但代价是更高的信任复杂度与不同的安全模型。带着本篇建立的「信任边界」直觉去读，会理解得更深。
综合练习：选一个你最看好的生态方案，写一段 200 字的产品说明，明确告诉用户「我把你的资产托付给了谁、什么情况下可能损失、你该怎么备份」。能把这一步说清楚的钱包，才配得上用户的信任。
