ETH 篇 I：概念与钱包开发

读懂「世界计算机」的运行规则，并用 Node.js + ethers v6 从零写出一个能签名、能转账、能监听入账的钱包。主要参考：《精通以太坊 Mastering Ethereum》开源版 github.com/ethereumbook/ethereumbook、ethereum.org/developers、EIPs。

本章目标：
  • 建立以太坊全局状态、账户、EVM、Gas 与 PoS 的体系化心智模型
  • 理解 EIP-1559 费用机制、交易生命周期与 nonce 防重放原理
  • 能用 ethers v6 完成助记词 HD 派生、地址校验和与三种签名
  • 能发送 EIP-1559 转账并加速/取消交易、解析回执与事件
  • 能用 keystore 加密备份、用 Provider 监听入账，并选型 RPC 服务商

1. 以太坊是什么：世界计算机与智能合约平台

比特币回答的问题是「没有银行也能记账」，而以太坊回答的是「没有中介也能运行程序」。以太坊是一个去中心化、图灵完备的状态机：全网节点按照确定性的规则，从同一个初始状态出发，逐块执行交易，最终达成一致的全局状态。这个状态机被形象地称为「世界计算机」（World Computer）。

一句话区分：比特币的脚本语言刻意做得非图灵完备，用来限制风险；以太坊则内置了图灵完备的虚拟机 EVM，让任何人都能部署「智能合约」（Smart Contract）——一段部署到链上、无人能单方面篡改、按代码自动执行的程序。

以太坊的关键抽象有五个：

抽象作用对比比特币
账户 Account状态的最小单元，含余额与（合约的）代码/存储比特币只有 UTXO，无账户
状态树 State Trie用 MPT 把全账户组织成可验证哈希树UTXO 集合，无统一状态根
EVM栈式虚拟机，执行合约字节码Script 非图灵完备
Gas计量计算/存储成本，防止滥用与死循环以「脚本大小/签名操作」粗略计费
交易 Transaction触发状态变更的消息（转账或调合约）交易本质是 UTXO 的消费与创建

「智能合约」一词源自 1990 年代 Nick Szabo 的设想，以太坊把它变成了现实：合约以 EVM 字节码形式存在，地址即其「身份证」，任何人都能向该地址发交易来调用它的函数。由于代码公开且全网重放执行，合约行为可审计、可组合（一个合约能调用另一个合约），这正是 DeFi「乐高」得以成立的基础。

「以太坊不是来颠覆某家银行，而是来替换整个后台清算层。」——理解这句话，你就能理解为什么 DeFi、NFT、稳定币都先出现在以太坊上。

2. 两类账户与全局状态

以太坊有两种账户，区别在于是否有代码：

维度外部账户 EOA（Externally Owned Account）合约账户 Contract Account
是否有私钥有，由用户掌握无，由代码控制
能否发起交易能（交易的源头）不能，只能被交易或别的合约调用
是否有代码无，codeHash 为空有，codeHash 指向代码哈希
是否有存储无，storageRoot 为空有，storageRoot 指向存储树
创建方式由私钥生成地址，无需上链由 EOA 发交易（CREATE/CREATE2）部署
地址来源公钥 Keccak256 取后 20 字节部署者地址+nonce 哈希 / CREATE2 公式
常见误区：「钱包」在以太坊里并不是一个链上实体，而是一组密钥 + 一个 EOA 地址的本地管理工具。所谓「钱包余额」就是该 EOA 的 balance 字段；所谓「代币余额」其实存在某个 ERC20 合约的存储里，只是按你的地址做索引。

2.1 全局状态与存储树（MPT 概念）

以太坊在每个区块头保存三个根哈希，构成「世界状态」的可验证指纹：

  • stateRoot：所有账户组成的 Merkle Patricia Trie（MPT）根。账户字段（nonce/balance/storageRoot/codeHash）被序列化后存入。
  • storageRoot：合约内部存储（slot → value 的键值对）各自的 MPT 根。每个合约拥有一棵独立存储树。
  • transactionsRoot / receiptsRoot：本区块交易与回执各自的 MPT 根。

MPT 同时具备「前缀压缩树」与「默克尔树」的特性：既能高效检索键值，又能用一条 Merkle 证明（几个哈希）向轻客户端证明「某地址的余额确实是 X」。这正是轻钱包无需下载全量数据也能验证状态的原因。

直觉理解：把 stateRoot 想象成整本账本的「指纹」。任意一处账户余额改动，stateRoot 都会变；你只要相信区块头里的 stateRoot，再拿到一条 Merkle 证明，就能确认某条具体状态，而不必相信某个中心化服务器。

3. EVM、Gas 与 EIP-1559 费用机制

3.1 EVM：栈式虚拟机与 opcode

EVM 是一个基于栈（stack-based）的虚拟机，不是基于寄存器的。它有一个 1024 深的栈、临时内存（memory，易失）和持久存储（storage，按合约持久化、极贵）。合约源码（Solidity）被编译为 opcode 字节码，例如：

opcode含义基础 Gas
ADD栈顶两数相加3
MSTORE写入内存3
SSTORE写入存储（新值）最多 20000（冷）/5000（热）
SLOAD读取存储100（热）/2100（冷）
CALL调用另一合约至少 100 + 被调消耗
SHA3 (KECCAK256)哈希30 + 每字 6

EVM 是确定性的：同一笔交易在任意全节点上执行，结果（含 Gas 消耗）必须完全一致，否则节点无法达成共识。这也意味着合约里不能使用随机数、系统时间等不确定来源，只能使用区块内的确定字段（如 block.timestamp、block.number、blockhash）。

3.2 Gas 机制三件套

  • gasLimit：你愿意为这笔交易最多消耗的 Gas 量（防死循环）。EVM 跑完若超量即回滚，但已耗 Gas 不退。
  • gasUsed：交易实际消耗的 Gas。未用完的部分（gasLimit - gasUsed）× 单价会退回。
  • Gas 单价（price）：每单位 Gas 付多少 ETH。在 EIP-1559 前后算法不同（见下）。

3.3 EIP-1559：base fee 销毁 + priority fee

2021 年伦敦硬分叉引入 EIP-1559，把「单一 Gas 价格」拆成两块：

字段含义归属
baseFeePerGas由协议按上一区块利用率自动调节（满则升、空则降，目标 50% 利用率）被销毁（burn），不归矿工/验证者
maxPriorityFeePerGas你额外给验证者的「小费」，用于插队归打包该块的验证者
maxFeePerGas你愿意支付的总单价上限baseFee + priority 实际取小

实付单价 = min(maxFeePerGas, baseFeePerGas + maxPriorityFeePerGas)。由于 baseFee 被销毁，ETH 在高负载时会出现通缩压力，这是 EIP-1559 的宏观外溢效应。

3.4 Legacy 交易 vs EIP-1559 交易对照

字段Legacy（类型 0）EIP-1559（类型 2）
gasPrice单一单价—
maxFeePerGas—有
maxPriorityFeePerGas—有
type 字节无前缀（0x 起）0x02 前缀
费用去向全部给矿工baseFee 销毁 + 小费给验证者
钱包开发建议：现代钱包默认构造 EIP-1559 交易（type 2），并用 eth_feeHistory 估算 baseFee，配合一个合理的 priority 即可。仅在与老旧设施兼容时才回退 legacy。

4. 交易生命周期、nonce 与最终性

4.1 交易生命周期

  1. 签名：EOA 用私钥对交易哈希签名（含 chainId 防重放）。
  2. 广播 / mempool：交易进入节点的待打包内存池（mempool），公开可见。
  3. 打包：验证者选中交易放进区块，执行并消耗 Gas。
  4. 确认：区块上链，交易获得第 1 个确认。
  5. 最终性（finality）：PoS 下经若干 epoch 后区块被标记为 justified / finalized，几乎不可回滚。

4.2 nonce 与 EIP-155 链 ID 防重放

每个 EOA 有一个从 0 递增的 nonce，代表「已发出的交易数」。节点只接受 nonce == 当前账户 nonce 的交易，且必须按序执行——这保证了「同一笔交易不会被重复执行两次」。

EIP-155：早期以太坊没有链 ID 概念，导致在 ETH 上签的交易可被重放到 ETC（分叉链）。EIP-155 把 chainId 纳入签名摘要，使签名绑定到特定链。Sepolia 测试网 chainId = 11155111，主网 = 1。

4.3 PoS 最终性：slot / epoch / justified / finalized

概念时长含义
slot12 秒一个验证者被随机选中进行出块的机会窗口
epoch32 slots = 6.4 分钟最终性投票的结算单位
justified—超过 2/3 验证者投票认可的检查点
finalized—已被一个 justified 检查点「背书」的检查点，视为不可逆

实践上，钱包通常把「12 个区块确认 / 约 2-3 分钟」作为足够安全的阈值；涉及大额则等 finalized（2 个 epoch ≈ 12.8 分钟）。

5. 收据、事件日志与区块结构

5.1 收据与事件日志

交易执行后产生收据（Receipt），包含：状态回执码（成功/失败）、实际 gasUsed、以及本次交易发出的日志（logs）。日志就是合约里 emit 事件 产生的数据，结构为 [address, topics[], data]：

  • address：发出事件的合约。
  • topics[0]：事件签名的 Keccak256 哈希，用于筛选。
  • topics[1..]：被标记为 indexed 的参数（最多 3 个），可精确过滤。
  • data：未被 indexed 的参数（ABI 编码的字节，不可直接过滤但可解码）。

5.2 Bloom 过滤器

每个区块头含一个 2048 位的 logsBloom。节点先用 Bloom 过滤器快速「粗筛」某事件/某地址是否可能出现在该块；若命中再精查日志。这让轻客户端高效订阅事件成为可能，代价是 Bloom 可能误报（但不会漏报）。

5.3 区块结构

区块头字段含义
parentHash父块哈希，串成链
stateRoot执行后状态树根
transactionsRoot交易树根
receiptsRoot回执树根
logsBloom事件 Bloom 过滤器
baseFeePerGas本块 EIP-1559 base fee
timestamp / number出块时间与高度

6. 共识与分层：PoS 与 L2 概览

6.1 PoS 简述

以太坊于 2022 年「合并（The Merge）」后由 PoW 转为权益证明（PoS）：

  • 验证者（Validator）：质押 32 ETH 即可运行节点参与出块与投票。
  • 罚没（Slashing）：若验证者作恶（双签、长期离线），会被罚没部分乃至全部质押，并强制退出。
  • 普通用户可用 Lido 等做流动性质押，低于 32 ETH 也能参与。

6.2 L2 概览：Optimistic vs ZK Rollup

主网（L1）昂贵且慢，L2 把大量交易在链下执行、只把压缩后的数据 + 证明提交回 L1，从而继承 L1 安全性又大幅降本。两大路线：

维度Optimistic RollupZK Rollup
安全性假设欺诈证明：默认诚实，挑战期（约 7 天）内可被质疑有效性证明：每批都附带零知识证明，数学保证正确
提款到 L1需等待挑战期（慢）证明验证通过即可（快）
EVM 兼容高（几乎原生 EVM）早期弱，现多有 zkEVM
代表Arbitrum、OP Mainnet（Optimism）、BasezkSync Era、Starknet、Linea、Scroll
开发体验合约可直接搬（同 Solidity）多数兼容 Solidity，个别需特定编译器
钱包开发提示：钱包只要把 RPC 指向 L2 的 endpoint（如 Base 的 chainId=8453），其余 ethers 调用与主网完全一致——以太坊的账户/交易模型在 L2 上复用。跨 L1/L2 的「桥」才是复杂点。

7. EIP-55 地址校验和

以太坊地址是 20 字节（40 个十六进制字符）。裸地址大小写不敏感，但 EIP-55 用 Keccak256 对地址做哈希，按哈希结果把某些字符转为大写，形成「校验和地址」。若用户输入时写错一位，校验和几乎必然不匹配，从而能拦截常见拷贝错误。

形式示例（前若干位）用途
全小写0x5aae6b2b...（无校验）不推荐，无法检错
EIP-55 混合大小写0x5AAE6b2b...（可校验）UI 展示、人工核对
注意：链上比较地址时一律按小写（无校验和）处理；EIP-55 只对「展示与人工输入」有意义，发送交易不会因为大小写而失败或成功。

8.2 HD 钱包派生（BIP-39 + BIP-44）

以太坊钱包通常遵循 BIP-39（助记词→种子）与 BIP-44（分层路径）。标准以太坊路径为 m/44'/60'/0'/0/0：

段含义
m主节点
44'用途（BIP-44）
60'币种（60 = ETH，SLIP-44 编号）
0'账户索引
0找零链（0=外部地址，1=内部找零）
0地址索引（第 0 个地址）

完整派生代码：

// hd-wallet.js
// 用助记词派生出第 0 个以太坊地址，与 MetaMask 默认账户一致
import { ethers } from "ethers";
import "dotenv/config";

const MNEMONIC = process.env.MNEMONIC;

// 1) 从助记词得到 BIP-39 种子（64 字节）
const seed = ethers.Mnemonic.fromPhrase(MNEMONIC).computeSeed();

// 2) 构造 HD 节点，沿 BIP-44 以太坊路径派生
//    ethers v6 的 HDNode 直接支持 path 派生
const path = "m/44'/60'/0'/0/0";
const hdNode = ethers.HDNodeWallet.fromPhrase(MNEMONIC, undefined, path);

console.log("派生路径:", hdNode.path);
console.log("私钥:", hdNode.privateKey);
console.log("地址(EIP-55):", hdNode.address);
console.log("地址(小写):", hdNode.address.toLowerCase());

// 3) 一次性派生同一助记词下的多个地址（账户浏览）
const base = ethers.HDNodeWallet.fromPhrase(MNEMONIC);
for (let i = 0; i < 3; i++) {
  const w = base.derivePath(`m/44'/60'/0'/0/${i}`);
  console.log(`地址[${i}]:`, w.address);
}
验证：用上面的测试助记词（BIP-39 标准测试向量），派生出的第 0 地址应为 0x5aAeb6b2b3e1d8e8a1b3f3c0c0e3a7d2E0d3C9e0 的对应值；可与 MetaMask / ganache 对照。生产环境务必替换为随机生成的助记词。

8.3 地址 checksum 编解码

手动实现 EIP-55 校验和，理解其本质：

// checksum.js
// 手写 EIP-55 校验和，等价于 ethers.getAddress()
import { ethers } from "ethers";

function toChecksumAddress(addr) {
  // 去掉 0x 并转小写
  const lower = addr.replace(/^0x/i, "").toLowerCase();
  if (lower.length !== 40) throw new Error("地址长度必须为 20 字节");

  // 对小写地址做 Keccak256，得到哈希的十六进制字符串
  const hash = ethers.keccak256(ethers.toUtf8Bytes(lower)).slice(2);

  let out = "0x";
  for (let i = 0; i < 40; i++) {
    const ch = lower[i];
    // 字母 a-f 才可能被大写；数字保持原样
    if (/[a-f]/.test(ch)) {
      // 哈希对应 nibble >= 8 则大写
      const nibble = parseInt(hash[i], 16);
      out += nibble >= 8 ? ch.toUpperCase() : ch;
    } else {
      out += ch;
    }
  }
  return out;
}

// 校验：传入混合大小写地址，校验是否合法
function verifyChecksum(addr) {
  return toChecksumAddress(addr) === addr;
}

const a = "0x5aaeb6b2b3e1d8e8a1b3f3c0c0e3a7d2e0d3c9e0";
const c = toChecksumAddress(a);
console.log("小写:", a);
console.log("校验和:", c);
console.log("校验通过:", verifyChecksum(c));
// ethers 自带等价方法
console.log("ethers.getAddress:", ethers.getAddress(a) === c);

console.log("chainId:", net.chainId, "name:", net.name);
console.log("最新高度:", block.number, "baseFee:", block.baseFeePerGas?.toString());

const address = "0x5aAeb6b2b3e1d8e8a1b3f3c0c0e3a7d2e0d3c9e0";
const bal = await provider.getBalance(address);
console.log("余额(wei):", bal.toString());
console.log("余额(eth):", ethers.formatEther(bal));

9. 三种签名：personal_sign / TypedData / SIWE

9.1 EIP-191 personal_sign（裸签名）

personal_sign 在消息前加 \x19Ethereum Signed Message:\n 固定前缀再哈希，避免「用交易签名私钥去签一段恶意交易字节」的误用。适合登录、对消息背书。

// sign-personal.js
import { ethers } from "ethers";
import "dotenv/config";

const wallet = ethers.HDNodeWallet.fromPhrase(process.env.MNEMONIC, undefined, "m/44'/60'/0'/0/0");

// 1) 对一段文本签名
const message = "登录 tutorial-dapp，时间 2025-01-01";
const signature = await wallet.signMessage(message);
console.log("签名:", signature);

// 2) 恢复签名者地址，验证确实由该钱包签署
const recovered = ethers.verifyMessage(message, signature);
console.log("恢复地址:", recovered);
console.log("匹配:", recovered === wallet.address);

// 3) 底层原理：personal_sign 实际签名的是带前缀的哈希
const prefixed = ethers.hashMessage(message); // 即 keccak256("\x19Ethereum Signed Message:\n" + len + msg)
console.log("消息哈希(EIP-191):", prefixed);

9.2 EIP-712 eth_signTypedData_v4（结构化签名）

裸签名对人类不可读、易误签。EIP-712 让你签名结构化、带类型的对象，钱包会显示可读字段。完整四要素：domain（防跨域/跨合约）、types（结构定义）、message/value（具体数据）、primaryType。

// sign-typeddata.js
import { ethers } from "ethers";
import "dotenv/config";

const wallet = ethers.HDNodeWallet.fromPhrase(process.env.MNEMONIC, undefined, "m/44'/60'/0'/0/0");

// 1) 定义 domain：把签名绑定到具体 dApp 与链，防重放/误用
const domain = {
  name: "Tutorial DApp",
  version: "1",
  chainId: 11155111,            // Sepolia
  verifyingContract: "0x0000000000000000000000000000000000000000",
};

// 2) 定义类型（注意 EIP-712 需要 EIP712Domain 与 Mail 两套结构）
const types = {
  EIP712Domain: [
    { name: "name", type: "string" },
    { name: "version", type: "string" },
    { name: "chainId", type: "uint256" },
    { name: "verifyingContract", type: "address" },
  ],
  Order: [
    { name: "maker", type: "address" },
    { name: "taker", type: "address" },
    { name: "token", type: "address" },
    { name: "amount", type: "uint256" },
    { name: "deadline", type: "uint256" },
  ],
};

// 3) 具体要签的 value
const value = {
  maker: wallet.address,
  taker: "0x0000000000000000000000000000000000000000",
  token: "0x5aAeb6b2b3e1d8e8a1b3f3c0c0e3a7d2e0d3c9e0",
  amount: ethers.parseUnits("100", 18),
  deadline: 1735689600,
};

// 4) 签名（ethers v6 的 signTypedData）
const signature = await wallet.signTypedData(domain, types, value);
console.log("EIP-712 签名:", signature);

// 5) 验证：恢复签名者，合约侧也可用 ecrecover 同样恢复
const recovered = ethers.verifyTypedData(domain, types, value, signature);
console.log("恢复地址:", recovered, "匹配:", recovered === wallet.address);

// 6) 计算结构化数据的 digest（合约端 ecrecover 用的哈希）
const digest = ethers.TypedDataEncoder.hash(domain, types, value);
console.log("结构化哈希:", digest);
合约端对应：在 Solidity 里用 ECDSA.recover(_hashTypedDataV4(digest), sig) 即可恢复 signer。digest = keccak256(abi.encodePacked("\x19\x01", hash(domain), hash(struct)))，ethers 的 TypedDataEncoder.hash 与之完全一致。

9.3 EIP-4361 SIWE（Sign-In with Ethereum）

SIWE 把「登录」标准化为一条可读的 EIP-712 消息（RFC 风格的明文 + 结构化字段），用于 Web2 风格的会话鉴权，而不必自建账号体系。

// siwe.js
// 构造并签名一个 SIWE 消息（简化版，生产请用 siwe 库）
import { ethers } from "ethers";
import "dotenv/config";

const wallet = ethers.HDNodeWallet.fromPhrase(process.env.MNEMONIC, undefined, "m/44'/60'/0'/0/0");

// SIWE 消息是一段结构化纯文本，字段由 EIP-4361 规定
const domain = "tutorial-dapp.example";
const address = wallet.address;
const statement = "登录 Tutorial DApp，仔细阅读不要授权任何交易。";
const uri = "https://tutorial-dapp.example/login";
const version = "1";
const chainId = 11155111;
const nonce = "abc123def456";          // 必须由服务端下发，防重放
const issuedAt = new Date().toISOString();

const message = [
  `${domain} 想让你用你的以太坊账户登录。`,
  ``,
  `URI: ${uri}`,
  `版本: ${version}`,
  `链 ID: ${chainId}`,
  `地址: ${address}`,
  ``,
  `说明: ${statement}`,
  ``,
  `随机数: ${nonce}`,
  `签发时间: ${issuedAt}`,
].join("\n");

const signature = await wallet.signMessage(message);
console.log("SIWE 消息:\n" + message);
console.log("签名:", signature);
console.log("服务端应保存 nonce 与 signature，后续用 verifyMessage 校验。");
最佳实践：生产环境直接 npm install siwe，用 new SiweMessage(...).prepareMessage() 与 verify({ signature, nonce })，避免手拼格式出错。

10. 发送 EIP-1559 转账与加速取消

10.1 估算费用并发送转账

// send-1559.js
import { ethers } from "ethers";
import "dotenv/config";

const provider = new ethers.JsonRpcProvider(process.env.SEPOLIA_RPC);
const wallet = new ethers.Wallet(process.env.MNEMONIC, provider); // 也可 fromPhrase

// 1) 用 eth_feeHistory 估算最近的 base fee 走势
const feeData = await provider.getFeeData();
console.log("maxFeePerGas:", feeData.maxFeePerGas?.toString());
console.log("maxPriorityFeePerGas:", feeData.maxPriorityFeePerGas?.toString());

// 2) 手动设置：小费 2 gwei，总上限取 baseFee*1.5 + 小费（更稳）
const block = await provider.getBlock("latest");
const baseFee = block.baseFeePerGas;
const priority = ethers.parseUnits("2", "gwei");
const maxFee = baseFee * 3n / 2n + priority;

// 3) 构造 EIP-1559 转账交易（type 2）
const tx = {
  type: 2,
  to: "0x0000000000000000000000000000000000000000", // 测试：转给 0 地址
  value: ethers.parseEther("0.001"),
  maxFeePerGas: maxFee,
  maxPriorityFeePerGas: priority,
  // gasLimit 可省略，ethers 会自动估算；此处显式给出
  gasLimit: 21000,
  chainId: 11155111,
};

console.log("广播中... nonce =", await wallet.getNonce());
const sent = await wallet.sendTransaction(tx);
console.log("交易哈希:", sent.hash);

// 4) 等待上链并拿到回执
const receipt = await sent.wait();
console.log("区块高度:", receipt.blockNumber, "实际 gasUsed:", receipt.gasUsed.toString());
console.log("状态:", receipt.status === 1 ? "成功" : "失败");

10.2 交易加速（Replace-by-Fee）与取消

若交易长时间未打包（mempool 拥堵），可用同一 nonce、更高 priority fee 重发一笔交易来「插队」；若要取消，则向自己转 0 值、同样提费。原理：节点看到同 nonce 的新交易会替换旧的。

// replace-tx.js
import { ethers } from "ethers";
import "dotenv/config";

const provider = new ethers.JsonRpcProvider(process.env.SEPOLIA_RPC);
const wallet = new ethers.Wallet(process.env.MNEMONIC, provider);

// 场景：之前发的交易卡住了（已知其 nonce 与哈希）
const stuckNonce = await wallet.getNonce("latest"); // 假设卡在 latest nonce

const block = await provider.getBlock("latest");
const baseFee = block.baseFeePerGas;
// 加速：小费给到原来的 ~2 倍，确保优先打包
const priority = ethers.parseUnits("4", "gwei");
const maxFee = baseFee * 2n + priority;

// 加速：发一笔真实转账，同 nonce、更高费用
const speedUp = await wallet.sendTransaction({
  type: 2,
  to: "0x5aAeb6b2b3e1d8e8a1b3f3c0c0e3a7d2e0d3c9e0",
  value: ethers.parseEther("0.001"),
  nonce: stuckNonce,
  maxFeePerGas: maxFee,
  maxPriorityFeePerGas: priority,
  gasLimit: 21000,
});

// 取消：向自己转 0，同 nonce、更高费用，原交易将被挤出 mempool
const cancel = await wallet.sendTransaction({
  type: 2,
  to: wallet.address,
  value: 0n,
  nonce: stuckNonce,
  maxFeePerGas: maxFee * 2n / 3n + priority,
  maxPriorityFeePerGas: priority,
  gasLimit: 21000,
});

console.log("加速交易:", speedUp.hash);
console.log("取消交易:", cancel.hash, "（两者同 nonce，谁先上链另一个即失效）");
坑：替换交易的费用必须「严格更高」（EIP-1559 要求新 maxPriorityFeePerGas ≥ 旧值 + 1，且 maxFeePerGas ≥ 旧值）。否则节点会拒绝替换。务必先记录原 nonce。

  }

11.2 keystore JSON 加密导出与导入

keystore 是把私钥用密码（scrypt/kdf）加密后的 JSON 文件，可安全备份到磁盘/云。ethers 提供 Wallet.encrypt 与 fromEncryptedJson。

// keystore.js
import { ethers } from "ethers";
import { writeFileSync, readFileSync } from "fs";

const wallet = ethers.HDNodeWallet.fromPhrase(process.env.MNEMONIC, undefined, "m/44'/60'/0'/0/0");
const password = "你的强密码";

// 1) 导出加密 keystore
const json = await wallet.encrypt(password);
writeFileSync("keystore.json", json);
console.log("已导出 keystore.json（可离线保存）");

// 2) 用密码导入还原钱包
const data = readFileSync("keystore.json", "utf8");

console.log("还原地址:", restored.address, "一致:", restored.address === wallet.address);

// 3) 危险演示：从明文私钥直接构造（仅测试，生产严禁硬编码私钥）
const fromPk = new ethers.Wallet(wallet.privateKey);
console.log("私钥还原地址:", fromPk.address);
安全红线：私钥/助记词永远不要出现在日志、截图、聊天、代码仓库。keystore 的密码也要强且独立。前端（浏览器）里尽量用 window.ethereum（钱包注入）而非持有私钥。

13. 钱包架构与 EIP-4337 账户抽象

前面我们用的都是「EOA + 本地私钥」的传统钱包。现实中还有更多形态，理解它们有助于你设计产品形态：

钱包类型私钥位置特点 / 风险
热钱包（软件）联网设备方便，易被木马/钓鱼窃取；MetaMask 属此类
冷钱包（硬件）离线硬件（Ledger/Trezor）私钥永不触网，签名在设备上完成，最安全
观察钱包（watch-only）无私钥只读取余额/历史，用于监控
多签钱包分散在多人/多设备需 M-of-N 签名才动款，企业金库常用
智能合约钱包合约代码控制支持社交恢复、限额、批量交易（见下）

13.1 EIP-4337：把「账户」变成合约

原生以太坊的 EOA 有两大痛点：① 必须持有 ETH 付 Gas；② 私钥丢失即资产永久丢失。EIP-4337「账户抽象（Account Abstraction）」不改动共识层，而是引入一套去中心化基础设施，让「账户」本身可以是合约：

  • UserOperation：一种「伪交易」结构，描述「我想做什么」，而非传统签名交易。
  • Bundler（打包器）：把多个 UserOp 聚合成一笔真实交易发上链，并垫付 Gas。
  • EntryPoint：全网共享的 singleton 合约，统一校验并执行 UserOp。
  • Paymaster（代付者）：替用户代付 Gas，甚至允许用 ERC20 付手续费——实现「无 ETH 也能用」。
  • Aggregator：聚合签名，降低多签/多账户 Gas。
工程意义：账户抽象让钱包可以做到「社交恢复（失钥可找回）」「交易前风控」「批量授权+转账一步完成」。代表实现如 Safe（原 Gnosis Safe）与 Stackup/Candide 等 4337 栈。ethers 本身不直接处理 UserOp，需用 @account-abstraction/sdk 或 permissionless 等库，但底层仍复用本篇的 Provider / 签名原语。

13.2 本地密钥管理的最简封装

把本篇能力封装成一个可复用的钱包模块，便于后续篇章调用：

// wallet-factory.js
// 统一封装：助记词派生 / keystore 导入 / 连接 Provider
import { ethers } from "ethers";
import { readFileSync } from "fs";

export function fromMnemonic(mnemonic, rpc, path = "m/44'/60'/0'/0/0") {
  const provider = new ethers.JsonRpcProvider(rpc);
  const wallet = ethers.HDNodeWallet.fromPhrase(mnemonic, undefined, path);
  return wallet.connect(provider);
}

export async function fromKeystore(file, password, rpc) {
  const json = readFileSync(file, "utf8");
  const wallet = await ethers.Wallet.fromEncryptedJson(json, password);
  return wallet.connect(new ethers.JsonRpcProvider(rpc));
}

export function checksum(addr) {
  return ethers.getAddress(addr); // 自动做 EIP-55
}
