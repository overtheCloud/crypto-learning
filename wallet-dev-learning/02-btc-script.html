1. Script：一台栈式虚拟机

1.1 锁与钥匙的隐喻

上一篇讲过：UTXO 上带着一段 scriptPubKey（锁定脚本，业内也叫 witness/locking script），花费它的人必须提供 scriptSig 或 witness（解锁脚本）。验证过程 = 把解锁脚本的数据压入栈，然后执行锁定脚本，最后看栈顶是否为真。

历史演变：2010 年之前，节点是把 scriptSig + scriptPubKey 拼接后一次性执行的。这带来了严重漏洞（攻击者可以用 OP_TRUE 之类的手段绕过验证），所以现在改为两段式执行：先执行 scriptSig 得到初始栈，再用这个栈执行 scriptPubKey。SegWit 之后，见证数据栈直接作为初始栈。

1.2 逆波兰表示法（后缀表达式）

Script 是一种基于栈的、使用逆波兰表示法（Reverse Polish Notation）的语言：操作数先入栈，操作符从栈上取参数、算完把结果压回栈。计算 2 + 3 写作 2 3 OP_ADD。

# 表达式: (2 + 3) * 4 == 20  在 Script 中的写法与栈变化
脚本:  OP_2 OP_3 OP_ADD OP_4 OP_MUL OP_20 OP_EQUAL

指令        操作                          栈(左=底 右=顶)
--------------------------------------------------------
OP_2        压入常数 2                    [2]
OP_3        压入常数 3                    [2, 3]
OP_ADD      弹出 3、2，压入 5             [5]
OP_4        压入常数 4                    [5, 4]
OP_MUL      弹出 4、5，压入 20            [20]
OP_20       压入常数 20                   [20, 20]
OP_EQUAL    弹出两个，相等则压入 1        [1]
--------------------------------------------------------
执行结束，栈顶为 1（真）→ 脚本验证通过
注意：OP_MUL 等算术操作码在 2010 年因整数溢出安全隐患被永久禁用，上面只是教学示例。现存可用的算术操作码只有 OP_ADD、OP_SUB、OP_1ADD 等少数几个，且限制在 32 位有符号整数以内。

2. 为什么故意不做图灵完备

2.1 缺失的能力

Script 没有循环、没有递归、没有跳转到任意位置的能力。它只有前向的条件分支（OP_IF / OP_ELSE / OP_ENDIF），执行流永远从左到右单向推进。因此每个脚本的执行步数在解析时就有确定上界——这叫「可判定终止」。

2.2 三个理由

① 防 DoS

如果允许循环，一个 while(true) 脚本就能让全网每个验证节点挂死。以太坊用 gas 计价来解决，比特币选择从语言层面消除这种可能。

② 可预测的验证成本

节点必须能在打包前快速判断一笔交易的验证开销。无循环意味着开销与脚本长度线性相关，可直接用体积计费。

③ 减少攻击面

脚本越简单，形式化分析越容易，共识 bug 越少。比特币把「货币结算层」的可靠性放在表达力之上。

2.3 「非图灵完备」不等于「不能做复杂事」

缺少循环并不意味着表达力低下。实践中人们用这些技巧绕过限制：

  • 展开（unrolling）：固定次数的重复直接写 N 遍。
  • 把状态放在链外：闪电网络把绝大部分逻辑放到通道双方的本地状态机，链上只做最终仲裁。
  • 条件树（MAST）：Taproot 的脚本树相当于一次多路分支，把复杂策略拆成多条独立路径。
  • 协变量（covenants）模拟：通过预签名交易链条约束资金流向，如 Vaults 方案。
设计取向的差异：以太坊问「我们能表达什么」，比特币问「我们能安全地保证什么」。两者不是优劣，而是分层——结算层求稳，表达力交给 L2。

4. P2PKH 执行追踪（逐步栈变化）

这是必须完全掌握的基本功。假设：

scriptSig    (解锁): <sig> <pubKey>
scriptPubKey (锁定): OP_DUP OP_HASH160 <pubKeyHash> OP_EQUALVERIFY OP_CHECKSIG

4.1 阶段一：执行 scriptSig（构造初始栈）

步骤指令动作栈（左=底，右=顶）
0—初始状态[ ]
1push <sig>签名入栈（约 71–72 字节，含 SIGHASH 字节）[ sig ]
2push <pubKey>公钥入栈（压缩格式 33 字节）[ sig, pubKey ]

4.2 阶段二：执行 scriptPubKey

步骤指令动作栈
3OP_DUP复制栈顶 pubKey[ sig, pubKey, pubKey ]
4OP_HASH160弹出栈顶，压入 RIPEMD160(SHA256(pubKey))[ sig, pubKey, pubKeyHash' ]
5push <pubKeyHash>脚本中写死的 20 字节哈希入栈[ sig, pubKey, pubKeyHash', pubKeyHash ]
6OP_EQUALVERIFY弹出两个哈希比较；不等则立即失败，相等则继续（不留结果）[ sig, pubKey ]
7OP_CHECKSIG弹出 pubKey 与 sig，按 SIGHASH 计算交易摘要并验签，成功压入 1[ 1 ]
8结束栈中只剩一个元素且为真 → 验证通过[ 1 ]
为什么第 6 步用 EQUALVERIFY 而不是 EQUAL？因为 EQUAL 会把布尔结果留在栈上，脚本结束时栈里会有两个元素（多余的 1 与 CHECKSIG 结果），在启用 CLEANSTACK 规则的 SegWit 中会被判为非标准。EQUALVERIFY 消耗掉结果，让脚本更干净、还省一个字节。

4.3 SIGHASH：签名到底签了什么

OP_CHECKSIG 验签时并不是对整笔交易原文签名，而是对一个按 SIGHASH 标志裁剪后的交易摘要签名。这决定了签名对交易哪些部分「负责」。

SIGHASH 标志值承诺范围用途
SIGHASH_ALL0x01所有输入 + 所有输出默认，最安全
SIGHASH_NONE0x02所有输入，不管输出危险：任何人可改收款地址
SIGHASH_SINGLE0x03所有输入 + 同索引的那一个输出原子交换、CoinJoin
+ ANYONECANPAY0x80只承诺自己这一个输入众筹、可追加输入的场景
SIGHASH_DEFAULT0x00Taproot 专用，等价于 ALL省 1 字节
BIP143（SegWit v0 签名哈希）的改进：旧算法在多输入交易中对每个输入都要重新序列化整笔交易，复杂度是 O(n²)，曾被用于 DoS。BIP143 引入 hashPrevouts、hashSequence、hashOutputs 三个可复用的中间哈希，把复杂度降到 O(n)；同时把被花费金额纳入签名，使离线签名器能独立确认自己签的是多少钱。

6. 交易延展性与 SegWit 原理

6.1 延展性问题是什么

交易延展性（transaction malleability）：在不改变交易语义、不需要私钥的前提下，第三方（包括矿工、中继节点）能修改交易的字节表示，从而改变 txid。

根源在于：txid = 双 SHA256(整笔交易序列化)，而序列化里包含了 scriptSig——签名本身不可能对自己所在的位置签名。可被修改的地方包括：

  • ECDSA 签名的 (r, s) 与 (r, −s mod n) 都是合法签名（低 s 值规范化前）。
  • DER 编码的填充与长度表示存在多种等价写法。
  • 可在 scriptSig 前插入无副作用的操作码（如 OP_NOP、多余的 push）。

6.2 造成的实际危害

场景危害
交易所提现后台按 txid 追踪，txid 变了误判为「未发出」而重复发送（Mt.Gox 事件的原因之一）
链式交易子交易引用父交易 txid；父 txid 一变，整条未确认交易链全部失效
支付通道闪电网络的承诺交易必须预先引用资金交易的 txid——延展性让「预签名未广播交易」这一模式根本无法安全成立
关键因果链：没有 SegWit 修好延展性，就不可能有闪电网络。这是 SegWit 最重要的连带价值，远超「省手续费」。

6.3 SegWit 的解法：把见证数据搬出去

# 传统交易的序列化（txid 覆盖全部内容，含签名）
[version][vin_count][txid|vout|scriptSig|sequence]...[vout_count][value|scriptPubKey]...[locktime]
                                   ^^^^^^^^^ 签名在这里，所以改签名 → txid 变

# SegWit 交易的序列化
[version][marker=0x00][flag=0x01][vin_count][txid|vout|scriptSig(空)|sequence]...
         [vout_count][value|scriptPubKey]...[witness数据...][locktime]

txid  = hash256( 去掉 marker/flag/witness 的序列化 )   ← 不含签名，无法被延展
wtxid = hash256( 完整序列化，含 witness )               ← 含签名，用于见证承诺

要点：

  1. txid 不再覆盖签名：签名怎么改都不影响 txid，延展性问题根治。
  2. wtxid 的 Merkle 根写进 coinbase：通过 coinbase 的一个 OP_RETURN 输出承诺见证数据，保证矿工不能随意丢弃 witness，同时对老节点保持兼容（老节点看到的是一个普通的不可花费输出）。
  3. 见证数据享受 75% 折扣：weight = base×3 + total 意味着 witness 字节只按 1/4 计费。这是对「把签名搬到区块另一个区域」这一行为的经济激励。
  4. 向后兼容的软分叉：老节点看 P2WPKH 的锁定脚本 OP_0 <20字节>，会理解为「压入 0，压入 20 字节数据，脚本结束，栈顶为真」→ 判定为任何人可花费。新节点则施加严格的见证验证规则。因此只要多数算力升级，就是安全的软分叉。
版本位与「任何人可花费」：SegWit 输出对老节点来说是 anyone-can-spend。这也是为什么 SegWit 激活需要绝大多数算力支持——如果多数矿工不执行新规则，SegWit 资金真的会被任意花掉。同理，Taproot 输出 OP_1 <32字节> 对未升级到 Taproot 的节点也是 anyone-can-spend。

7.4 MAST：Merkle 抽象语法树

过去用 OP_IF 写多条件脚本，所有分支都必须写进脚本、全部公开、全部计费。MAST 把每个分支（叫 leaf script / tapleaf）单独哈希，组成 Merkle 树，只把树根承诺进输出。花费时只需揭示实际使用的那一条分支加上 Merkle 路径。

# Taproot 输出公钥的构造
internal_pubkey  P        (32 字节 x-only，可以是 MuSig2 聚合公钥)
tapleaf 脚本     S1, S2, S3 ...
leaf_hash_i    = tagged_hash("TapLeaf", leaf_version || compact_size(Si) || Si)
merkle_root  m = 逐层 tagged_hash("TapBranch", sort(左,右))
tweak        t = tagged_hash("TapTweak", P || m)
output_pubkey Q = P + t*G          # 这就是写进 scriptPubKey 的 32 字节

scriptPubKey = OP_1 <Q>             # 即 51 20 <32字节>

7.5 两条花费路径

密钥路径（Key Path）脚本路径（Script Path）
见证内容1 个元素：64 字节 Schnorr 签名参数… + leaf 脚本 + 控制块
使用条件知道 P 对应私钥（经 t 调整后）满足某条 tapleaf 脚本的条件
控制块不需要33 + 32×深度 字节：含 leaf 版本、P、Merkle 路径
成本最低（约 57.5 vB 输入）较高，随脚本与路径长度增长
隐私最佳，与普通转账无异只暴露被使用的那一条分支
设计建议把「最常用、最合作」的场景放这里把「异常、争议、超时」的兜底逻辑放这里
// taproot-demo.js —— 构造一个带脚本树的 P2TR 地址（密钥路径 + 两条备用分支）
const { bitcoin, ECPair, NETWORK } = require('./setup');   // setup.js 见第一篇
const toXOnly = (pubkey) => pubkey.subarray(1, 33);        // 33 字节压缩 → 32 字节 x-only

const internalKey = ECPair.makeRandom({ network: NETWORK });   // 常用路径（可为 MuSig2 聚合）
const backupKey   = ECPair.makeRandom({ network: NETWORK });   // 备用恢复钥匙
const escrowKey   = ECPair.makeRandom({ network: NETWORK });   // 仲裁方

// 分支 1：144 个区块（约 1 天）之后，备用钥匙可单独花费（CSV 相对时间锁）
const leaf1 = bitcoin.script.fromASM(
  ('90 OP_CHECKSEQUENCEVERIFY OP_DROP ' + toXOnly(backupKey.publicKey).toString('hex') +
   ' OP_CHECKSIG').replace(/\s+/g, ' ')
);   // 0x90 = 144

// 分支 2：备用钥匙 + 仲裁方同时签名（用 Tapscript 的 CHECKSIGADD 做 2-of-2）
const leaf2 = bitcoin.script.fromASM(
  (toXOnly(backupKey.publicKey).toString('hex') + ' OP_CHECKSIG ' +
   toXOnly(escrowKey.publicKey).toString('hex') + ' OP_CHECKSIGADD OP_2 OP_NUMEQUAL')
);

// 组装脚本树：数组结构即 Merkle 树（bitcoinjs 会自动排序并计算 root）
const scriptTree = [
  { output: leaf1 },
  { output: leaf2 }
];

const p2tr = bitcoin.payments.p2tr({
  internalPubkey: toXOnly(internalKey.publicKey),
  scriptTree,
  network: NETWORK
});
console.log('P2TR 地址(bc1p/tb1p) =', p2tr.address);
console.log('输出脚本 =', bitcoin.script.toASM(p2tr.output));   // OP_1 <32字节Q>

// 若要走脚本路径花费，需要 redeem 指定用哪一个 leaf，库会生成对应控制块
const p2trSpendLeaf1 = bitcoin.payments.p2tr({
  internalPubkey: toXOnly(internalKey.publicKey),
  scriptTree,
  redeem: { output: leaf1, redeemVersion: 192 },   // 192 = 0xc0，Tapscript leaf 版本
  network: NETWORK
});
console.log('分支1 控制块长度 =', p2trSpendLeaf1.witness.at(-1).length, '字节');
console.log('说明：控制块 = 33 + 32*树深度，本例深度 1 → 65 字节');
必须调用 bitcoin.initEccLib(ecc)：Taproot 需要椭圆曲线的点加与 tweak 运算，v6 若未初始化会抛出 No ECC Library provided。另外 x-only 公钥的转换不能忘——直接传 33 字节压缩公钥会得到错误的地址。

8. 时间锁：CLTV 与 CSV

8.1 四种时间锁机制

层级机制字段/操作码语义
交易级nLockTime交易的 locktime 字段整笔交易在某高度/时间之前无效
交易级nSequence (BIP68)输入的 sequence 字段该输入所花 UTXO 需成熟 N 块/N×512 秒
脚本级CLTV (BIP65)OP_CHECKLOCKTIMEVERIFY绝对：要求花费交易的 nLockTime ≥ 指定值
脚本级CSV (BIP112)OP_CHECKSEQUENCEVERIFY相对：要求该输入的 nSequence 表示的等待期 ≥ 指定值
交易级 vs 脚本级的关键区别：交易级时间锁由构建交易的人自己填，可以随意改；脚本级时间锁写在锁定脚本里，是强制的花费前置条件，任何人都绕不过。所以做真正的托管、继承、通道方案必须用 CLTV/CSV。

8.2 nSequence 的编码（BIP68）

# nSequence 32 位的语义（仅当交易 version >= 2 时启用相对时间锁）
bit 31        = 1 → 禁用相对时间锁（0xffffffff 即全禁用）
bit 22        = 类型标志：0 = 按区块数，1 = 按时间（每单位 512 秒）
bit 0..15     = 数值 N

示例：
0xffffffff  → 禁用一切（不启用 RBF，不启用相对锁）
0xfffffffe  → 启用 nLockTime，但不启用 RBF（BIP125 要求 < 0xfffffffe 才算 RBF 信号）
0xfffffffd  → 启用 RBF（最常用的"可替换"写法）
0x00000090  → 相对锁：等待 144 个区块（约 1 天）
0x00400090  → 相对锁：等待 144*512 秒 ≈ 20.5 小时

8.3 CLTV 实例：单方托管到期解锁

// timelock.js —— CLTV / CSV 脚本构造
const { bitcoin, ECPair, NETWORK } = require('./setup');
const alice = ECPair.makeRandom({ network: NETWORK });
const bob   = ECPair.makeRandom({ network: NETWORK });

// ---------- ① 纯 CLTV：区块高度 850000 之后 Alice 才能花 ----------
// 注意 CLTV 不弹栈，必须紧跟 OP_DROP 清理留下的数值
const cltvScript = bitcoin.script.compile([
  bitcoin.script.number.encode(850000),   // 小端最小编码，切勿手写十六进制
  bitcoin.opcodes.OP_CHECKLOCKTIMEVERIFY,
  bitcoin.opcodes.OP_DROP,
  alice.publicKey,
  bitcoin.opcodes.OP_CHECKSIG
]);
console.log('CLTV 脚本 =', bitcoin.script.toASM(cltvScript));

// ---------- ② 实用型：Bob 随时可花 / Alice 在高度 850000 之后可取回 ----------
// 这是"HTLC 的骨架"，也是继承钱包(dead man switch)的常见形态
const hodlOrRefund = bitcoin.script.compile([
  bitcoin.opcodes.OP_IF,
    bob.publicKey, bitcoin.opcodes.OP_CHECKSIG,          // 分支 A：Bob 立即取
  bitcoin.opcodes.OP_ELSE,
    bitcoin.script.number.encode(850000),
    bitcoin.opcodes.OP_CHECKLOCKTIMEVERIFY,
    bitcoin.opcodes.OP_DROP,
    alice.publicKey, bitcoin.opcodes.OP_CHECKSIG,        // 分支 B：Alice 超时退款
  bitcoin.opcodes.OP_ENDIF
]);
// 花费分支 A 的见证栈: [<bobSig>, 0x01]      （0x01 使 OP_IF 取真）
// 花费分支 B 的见证栈: [<aliceSig>, 空]      （空数组使 OP_IF 取假）
const p2wshHodl = bitcoin.payments.p2wsh({ redeem: { output: hodlOrRefund, network: NETWORK },
                                           network: NETWORK });
console.log('可退款托管地址 =', p2wshHodl.address);

// ---------- ③ CSV：资金到账后必须等 144 个区块 ----------
const csvScript = bitcoin.script.compile([
  bitcoin.script.number.encode(144),
  bitcoin.opcodes.OP_CHECKSEQUENCEVERIFY,
  bitcoin.opcodes.OP_DROP,
  alice.publicKey,
  bitcoin.opcodes.OP_CHECKSIG
]);
console.log('CSV 脚本 =', bitcoin.script.toASM(csvScript));

// ---------- ④ 花费时交易字段的强制要求 ----------
// 用 CLTV 花费：psbt.setLocktime(850000) 且该输入 sequence 必须 != 0xffffffff
// 用 CSV  花费：psbt.setVersion(2) 且该输入 sequence = 144 (0x00000090)
console.log('\n构建花费交易时的必填项：');
console.log('  CLTV → setLocktime(>=脚本值), sequence != 0xffffffff');
console.log('  CSV  → setVersion(2), sequence 编码的等待期 >= 脚本值');
最常见的三个时间锁 bug：① 用 CLTV 却忘了设置交易的 locktime → 脚本失败；② 输入 sequence 仍为 0xffffffff，导致 locktime 被忽略 → CLTV 失败；③ 用 CSV 却把交易 version 设为 1 → 相对时间锁不生效，节点按旧规则处理。

8.4 闪电网络为什么离不开时间锁

用途使用的机制作用
惩罚窗口（to_local 输出）CSV自己单方关闭通道后，资金需等待 N 块才能取走，给对方留出发现作弊并广播惩罚交易的时间
HTLC 超时退款CLTV如果收款方在约定高度前没揭示 preimage，付款方可拿回资金
多跳路由的 CLTV 递减CLTV路径上每一跳的超时高度依次减小（cltv_expiry_delta），保证上游总比下游晚过期，避免中间节点被夹在中间损失
撤销旧状态惩罚脚本 + CSV广播过期承诺交易的一方会被对手在 CSV 窗口内取走全部通道余额

9. 手续费急救：RBF 与 CPFP

9.1 两种方案对比

RBF（Replace-By-Fee, BIP125）CPFP（Child Pays For Parent）
谁能用发送方（需要控制原交易输入）任何有该交易输出的人，包括收款方
原理用更高费率的新交易替换内存池中的旧交易花掉未确认输出，构造高费率子交易，矿工为拿子交易的费必须一起打包父交易
前提原交易至少一个输入 sequence < 0xfffffffe你拥有该交易的某个输出（找零或收款）
成本较低，只付新交易的费较高，父+子两笔的总体积都要付费
txid变化（新交易新 txid）父交易 txid 不变
典型用途钱包"加速"按钮、改收款地址、撤销未确认支付收款方想尽快确认入账；交易所提现加速
Full-RBF 的变化：Bitcoin Core 24.0 起提供 mempoolfullrbf 选项，v28 起默认开启，意味着即使原交易没有设置 RBF 信号也可能被替换。因此商家绝不能把 0 确认交易当作最终支付。

9.2 BIP125 的五条替换规则

  1. 信号：原交易（或其未确认祖先）至少一个输入的 nSequence < 0xfffffffe。（full-RBF 节点会忽略此条。）
  2. 不新增未确认输入：替换交易不得引入原交易未曾使用过的未确认 UTXO。
  3. 绝对费更高：替换交易支付的总手续费必须高于所有被替换交易的总费之和。
  4. 额外带宽费：多出的手续费还必须 ≥ 替换交易体积 × 最低中继费率（默认 1 sat/vB）。
  5. 替换数量上限：被直接或间接替换的交易总数不得超过 100 笔。
规则 3 是绝对费而非费率，这是新手最容易踩的坑：如果替换交易体积变小（例如去掉了一个输入），即使费率翻倍，绝对费可能反而更低，节点会拒绝替换。写加速功能时务必同时校验「绝对费更高」和「费率更高」两个条件。

9.3 CPFP 的费率数学

# 场景：父交易 250 vB，只付了 250 聪（1 sat/vB），卡住了。
# 目标：让"父+子"这个打包组的整体费率达到 20 sat/vB。

设子交易体积 child_vsize = 150 vB
父+子总体积 = 250 + 150 = 400 vB
需要总费用 = 400 * 20 = 8000 聪
已付(父)   = 250 聪
子交易需付 = 8000 - 250 = 7750 聪
子交易自身费率 = 7750 / 150 ≈ 51.7 sat/vB   ← 子交易要付"超额"来拉高整组均值

结论：父交易费率越低、体积越大，CPFP 的救援成本越高。
矿工按"祖先/后代打包费率"(ancestor/descendant feerate)排序，
所以只有当整组费率进入区块门槛，两笔才会一起被打包。

10. PSBT（BIP174）角色与流程

10.1 PSBT 解决了什么

PSBT = Partially Signed Bitcoin Transaction，部分签名比特币交易。它是一种可序列化的交易构建中间态，携带了签名所需的全部上下文（被花费输出的脚本与金额、赎回脚本、BIP32 派生路径、已有的部分签名等）。在它出现之前，不同钱包/硬件之间交换未完成交易靠各家私有格式，几乎无法互操作。

10.4 冷热分离签名流程

热端（联网机器）

1. 用 watch-only 钱包（只有 xpub）查询 UTXO
2. 构建 PSBT，填齐元数据
3. 导出为 base64 文本 / 二维码 / SD 卡文件
4. 收回签名后的 PSBT，combine → finalize → 广播

冷端（永不联网）

1. 导入 PSBT
2. 在屏幕上逐项核对：收款地址、金额、找零地址、手续费
3. 用私钥签名
4. 只导出签名结果，私钥永不离开设备

11. 输出描述符与 watch-only 钱包

11.1 描述符要解决的问题

只有一个 xpub 是不够的：同一个 xpub 配不同的派生路径和脚本类型，可以生成 P2PKH、P2SH-P2WPKH、P2WPKH、P2TR 四套完全不同的地址。历史上无数「恢复钱包后余额为 0」的事故都源于此。输出描述符（Output Descriptors，BIP380–386）用一行字符串把「脚本类型 + 密钥来源 + 派生路径」全部说清楚。

11.2 语法与常用函数

# 基本形式：函数(密钥表达式)#校验和

单签钱包

助记词（+ passphrase）+ 派生路径。有描述符更稳妥。

多签钱包

12. Miniscript 简介

12.1 为什么需要它

手写 Script 有三个痛点：① 难以判断脚本是否「可花费」（有没有留下死锁）；② 无法自动算出最坏情况的见证体积（影响费率估算）；③ 无法自动生成解锁脚本，签名逻辑要一个个手写。

Miniscript 是 Script 的一个结构化子集，它保留了同样的表达力（针对实际用得上的策略），但具备可分析性：给定一个 Miniscript，工具可以机械地推导出正确性、可满足性、最大见证体积，并自动完成 finalize。

12.2 语法示例

# 策略(Policy)：人类描述 → 编译 → Miniscript → 编译 → Script

# 1) 单签
pk(A)                            →  <A> OP_CHECKSIG

# 2) 2-of-3 多签
thresh(2, pk(A), pk(B), pk(C))

# 3) "A 单独可花，或 B 在 144 块后可花"
or_d(pk(A), and_v(v:pk(B), older(144)))

# 4) HTLC：知道 preimage 立即拿走，或超时后退款
or_i(and_v(v:sha256(H), pk(收款方)), and_v(v:older(144), pk(付款方)))

# 5) 2-of-3 或者 时间锁后 1-of-3（继承 / 企业金库常用）
or_d(thresh(2, pk(A), pk(B), pk(C)),
     and_v(v:older(52560), thresh(1, pk(A), pk(B), pk(C))))
片段含义
pk(K)需要 K 的签名
older(n) / after(n)CSV 相对锁 / CLTV 绝对锁
sha256(h) / hash160(h)需提供哈希原像（HTLC 核心）
and_v / and_b逻辑与（不同栈语义）
or_b / or_d / or_i逻辑或（分别适合不同分支概率与体积权衡）
thresh(k, …)k-of-n 阈值
v: / s: / c: 等前缀类型转换包装，保证栈语义正确
生态现状：Bitcoin Core 从 24.0 起在描述符钱包中支持部分 Miniscript（wsh(...) 内）；rust-miniscript、BDK（Bitcoin Dev Kit）、Liana 钱包（继承/时锁恢复）都基于它。做复杂花费条件的钱包，优先考虑 Miniscript 而不是手搓 Script。

13. 实战①：手写迷你脚本解释器

没有比自己实现一遍解释器更能理解脚本执行的方式。下面这个约 100 行的解释器足以完整执行 P2PKH，并打印每一步的栈状态。

// mini-script-interpreter.js —— 迷你 Script 解释器，执行 P2PKH
// 运行：node mini-script-interpreter.js
const crypto = require('crypto');
const { bitcoin, ECPair, NETWORK } = require('./setup');   // setup.js 见第一篇

// ---------- 哈希工具 ----------
const sha256 = (b) => crypto.createHash('sha256').update(b).digest();
const ripemd160 = (b) => crypto.createHash('ripemd160').update(b).digest();
const hash160 = (b) => ripemd160(sha256(b));

// ---------- 栈元素的真假判定（与共识规则一致）----------
function castToBool(buf) {
  if (!buf || buf.length === 0) return false;
  for (let i = 0; i < buf.length; i++) {
    if (buf[i] !== 0) {
      // 负零（最后一字节为 0x80 且其余为 0）也算假
      if (i === buf.length - 1 && buf[i] === 0x80) return false;
      return true;
    }
  }
  return false;
}

const OPS = bitcoin.opcodes;   // 借用官方操作码常量表

/**
 * 执行一段脚本
 * @param {Array} chunks  bitcoin.script.decompile 的结果：Buffer 表示 push，number 表示操作码
 * @param {Array} stack   初始栈（Buffer 数组，末尾为栈顶）
 * @param {Function} checkSig  (sig, pubkey) => boolean，模拟签名验证
 */
function evaluate(chunks, stack, checkSig, label) {
  console.log('\n===== 执行 ' + label + ' =====');
  const dump = () => '[' + stack.map(x =>
      x.length > 8 ? x.toString('hex').slice(0, 8) + '..(' + x.length + 'B)'
                   : (x.length ? x.toString('hex') : 'EMPTY')).join(', ') + ']';
  console.log('  初始栈 ' + dump());

  for (const chunk of chunks) {
    // 情况一：chunk 是 Buffer → 数据入栈
    if (Buffer.isBuffer(chunk)) {
      stack.push(chunk);
      console.log('  PUSH(' + chunk.length + 'B)'.padEnd(18) + dump());
      continue;
    }
    // 情况二：chunk 是操作码
    switch (chunk) {
      case OPS.OP_DUP: {
        if (stack.length < 1) throw new Error('OP_DUP: 栈为空');
        stack.push(Buffer.from(stack[stack.length - 1]));   // 复制栈顶
        console.log('  OP_DUP'.padEnd(20) + dump());
        break;
      }
      case OPS.OP_HASH160: {
        const top = stack.pop();
        if (!top) throw new Error('OP_HASH160: 栈为空');
        stack.push(hash160(top));                          // RIPEMD160(SHA256(x))
        console.log('  OP_HASH160'.padEnd(20) + dump());
        break;
      }
      case OPS.OP_EQUAL:
      case OPS.OP_EQUALVERIFY: {
        const a = stack.pop(), b = stack.pop();
        if (!a || !b) throw new Error('OP_EQUAL*: 栈元素不足');
        const equal = a.equals(b);
        if (chunk === OPS.OP_EQUALVERIFY) {
          // VERIFY 变体：不等则整个脚本立即失败，相等则什么都不留
          if (!equal) throw new Error('OP_EQUALVERIFY 失败：公钥哈希不匹配');
          console.log('  OP_EQUALVERIFY'.padEnd(20) + dump() + '  (哈希匹配，继续)');
        } else {
          stack.push(Buffer.from([equal ? 1 : 0]));
          console.log('  OP_EQUAL'.padEnd(20) + dump());
        }
        break;
      }
      case OPS.OP_CHECKSIG: {
        const pubkey = stack.pop(), sig = stack.pop();
        const ok = checkSig(sig, pubkey);
        stack.push(ok ? Buffer.from([1]) : Buffer.alloc(0));   // 失败压入空数组(假)
        console.log('  OP_CHECKSIG'.padEnd(20) + dump() + '  (验签 ' + (ok ? '通过' : '失败') + ')');
        break;
      }
      case OPS.OP_VERIFY: {
        if (!castToBool(stack.pop())) throw new Error('OP_VERIFY 失败');
        console.log('  OP_VERIFY'.padEnd(20) + dump());
        break;
      }
      default:
        throw new Error('未实现的操作码: 0x' + chunk.toString(16));
    }
  }
  const result = stack.length === 1 && castToBool(stack[stack.length - 1]);
  console.log('  最终栈 ' + dump() + ' → ' + (result ? '脚本通过' : '脚本失败'));
  return result;
}

// ================= 构造一个真实的 P2PKH 场景 =================

14. 实战②：PSBT 三方多签协作

完整模拟 2-of-3 P2WSH 多签：Creator 建骨架 → Alice 与 Bob 在各自机器上签名 → Combiner 合并 → Finalizer → 广播。

// psbt-multisig-flow.js —— 2-of-3 P2WSH 多签的三方协作全流程
// 运行：node psbt-multisig-flow.js
const { bitcoin, ECPair, NETWORK } = require('./setup');

// ============ 第 0 步：三方各自离线生成密钥，只交换公钥 ============
// 生产环境：每个人在自己设备上生成，通过安全渠道交换 xpub/公钥
const alice = ECPair.makeRandom({ network: NETWORK });
const bob   = ECPair.makeRandom({ network: NETWORK });
const carol = ECPair.makeRandom({ network: NETWORK });

const pubkeys = [alice, bob, carol].map(k => k.publicKey).sort((a, b) => Buffer.compare(a, b));

                    : pk.equals(bob.publicKey) ? 'Bob' : 'Carol';
console.log('公钥排序结果:', pubkeys.map(whoIs).join(' < '));

const p2ms  = bitcoin.payments.p2ms({ m: 2, pubkeys, network: NETWORK });
const p2wsh = bitcoin.payments.p2wsh({ redeem: p2ms, network: NETWORK });

console.log('见证脚本   =', p2ms.output.toString('hex'), '(三方都必须备份!)');

psbtBase.addInput({

psbtA.signInput(0, alice);

const combined = bitcoin.Psbt.fromBase64(psbtFromAlice, { network: NETWORK });
combined.combine(bitcoin.Psbt.fromBase64(psbtFromBob, { network: NETWORK }));
console.log('  合并后签名数 =', combined.data.inputs[0].partialSig.length, '(需要 2)');

  console.log('    来自', whoIs(ps.pubkey), '签名', ps.signature.length, '字节'));

const validator = (pubkey, msghash, signature) =>
  ECPair.fromPublicKey(pubkey).verify(msghash, signature);
console.log('  签名验证 =', combined.validateSignaturesOfInput(0, validator));
combined.finalizeAllInputs();     // 组装 witness: [空, sigA, sigB, witnessScript]
console.log('  已 finalize');

// ============ 第 6 步：Extractor —— 提取并广播 ============
const tx = combined.extractTransaction();
console.log('\ntxid  =', tx.getId());
console.log('vsize =', tx.virtualSize(), 'vB | 实际费率 ≈',
            ((utxo.value - outTotal) / tx.virtualSize()).toFixed(2), 'sat/vB');
console.log('witness 栈元素数 =', tx.ins[0].witness.length,
            '(空占位 + 2 个签名 + witnessScript = 4)');
console.log('raw hex =', tx.toHex().slice(0, 120) + '...');
console.log('\n广播: POST https://mempool.space/testnet/api/tx  body=<上面的 hex>');

const { bitcoin, bip32, ECPair, NETWORK } = require('./setup');
const API = 'https://mempool.space/testnet/api';

const estimateVsize = (i, o) => Math.ceil(10.5 + 68 * i + 31 * o);
const MIN_RELAY_RATE = 1;    // sat/vB，BIP125 规则 4 用到

/**
 * 生成替换交易
 * @param {Object} original  原交易信息 {inputs:[{txid,vout,value}], toAddress, amount, fee, vsize}
 * @param {number} newFeeRate 目标费率 sat/vB
 */
function buildReplacement(original, newFeeRate, keyPair, changeAddress) {
  const payment = bitcoin.payments.p2wpkh({ pubkey: keyPair.publicKey, network: NETWORK });
  const inputSum = original.inputs.reduce((s, u) => s + u.value, 0);

  // 替换交易结构与原交易相同（同样的输入、同样的收款输出），只是找零变少、手续费变多
  const vsize = estimateVsize(original.inputs.length, 2);
  let newFee = Math.ceil(vsize * newFeeRate);

  // ---- BIP125 规则 3：绝对费必须高于被替换交易 ----
  if (newFee <= original.fee) {
    throw new Error('新手续费(' + newFee + ') 必须高于原手续费(' + original.fee + ')');
  }
  // ---- BIP125 规则 4：增量还要覆盖替换交易自身的带宽成本 ----
  const requiredIncrement = Math.ceil(vsize * MIN_RELAY_RATE);
  if (newFee - original.fee < requiredIncrement) {
    newFee = original.fee + requiredIncrement;    // 自动补足到最低可替换水平
    console.log('  按规则 4 自动上调手续费至', newFee, '聪');
  }

  const change = inputSum - original.amount - newFee;
  if (change < 294) throw new Error('加速后找零成为粉尘，请改用更少输出或补充 UTXO');

  const psbt = new bitcoin.Psbt({ network: NETWORK });
  psbt.setVersion(2);
  for (const u of original.inputs) {
    psbt.addInput({
      hash: u.txid, index: u.vout,
      witnessUtxo: { script: payment.output, value: u.value },
      sequence: 0xfffffffd            // ★ 替换交易本身也保持可替换，便于二次加速
    });
  }
  psbt.addOutput({ address: original.toAddress, value: original.amount });   // 收款额不变
  psbt.addOutput({ address: changeAddress, value: change });                 // 找零减少
  for (let i = 0; i < original.inputs.length; i++) psbt.signInput(i, keyPair);
  psbt.finalizeAllInputs();
  const tx = psbt.extractTransaction();
  return { tx, newFee, change, vsize: tx.virtualSize() };
}

15.1 什么时候该用 CPFP 而不是 RBF

  • 原交易没有设置 RBF 信号，且你连的节点未启用 full-RBF。
  • 你是收款方，没有原交易输入的私钥，只能花那个收款输出。
  • 原交易的输出已被下游依赖（改 txid 会打断链条）。
// cpfp.js —— 用子交易拉高父交易的打包费率（核心计算部分）
// 目标：让"父+子"这一组的整体费率达到 targetRate
function planCpfp({ parentVsize, parentFee, childVsize, targetRate }) {
  const totalVsize = parentVsize + childVsize;
  const totalFeeNeeded = Math.ceil(totalVsize * targetRate);
  const childFee = totalFeeNeeded - parentFee;
  if (childFee <= 0) return { needed: false, reason: '父交易费率已足够' };
  return {
    needed: true,
    childFee,
    childRate: +(childFee / childVsize).toFixed(2),
    packageRate: +(totalFeeNeeded / totalVsize).toFixed(2)
  };
}
// 父 250 vB 只付了 250 聪，子交易 150 vB，要把整组拉到 20 sat/vB
console.log(planCpfp({ parentVsize: 250, parentFee: 250, childVsize: 150, targetRate: 20 }));
// → { needed: true, childFee: 7750, childRate: 51.67, packageRate: 20 }

// 构建子交易的要点（代码结构与普通转账一致）：
// 1) 输入 = 父交易中属于自己的那个未确认输出（witnessUtxo 用父交易的 script/value）
// 2) 输出 = 一个自己的地址，金额 = 输入 - childFee
// 3) 注意 mempool 的祖先链限制：默认最多 25 笔祖先、101 kvB 总体积

16. 实战④：描述符导入 Bitcoin Core

# ---------- 第 1 步：创建一个 watch-only 描述符钱包 ----------
# disable_private_keys=true 让钱包只能观察，不能签名（冷热分离的热端）
bitcoin-cli -regtest -named createwallet \
  wallet_name="watch_only" \
  disable_private_keys=true \
  blank=true \
  descriptors=true

# ---------- 第 2 步：取到带校验和的规范描述符 ----------
# 手写的描述符没有校验和，导入会被拒绝；用 getdescriptorinfo 补上
DESC="wpkh([d34db33f/84h/1h/0h]tpubDCVFj1Y2AS4YbQfSPZQVBW8Ax9TE5EhVMhbxLNi9x2gTBqz1nsPtGvHFPvHbNMFvJEDPWaKfBTPGmYqK1F6mQTNiEcVQ/0/*)"
bitcoin-cli -regtest getdescriptorinfo "$DESC"
# 输出中的 "descriptor" 字段就是带 #checksum 的规范形式，复制它

# ---------- 第 3 步：导入收款链与找零链 ----------
# 一个钱包通常要导两条：internal=false(收款) 与 internal=true(找零)
bitcoin-cli -regtest -rpcwallet=watch_only importdescriptors '[
  {
    "desc": "wpkh([d34db33f/84h/1h/0h]tpub.../0/*)#checksum1",
    "active": true,
    "internal": false,
    "range": [0, 999],
    "timestamp": "now",
    "label": "receive"
  },
  {
    "desc": "wpkh([d34db33f/84h/1h/0h]tpub.../1/*)#checksum2",
    "active": true,
    "internal": true,
    "range": [0, 999],
    "timestamp": "now"
  }
]'
# timestamp: "now" 表示不回扫历史；若要找回旧资金，填该钱包创建时的 Unix 时间戳，
# Core 会从该时间点开始 rescan（耗时较长，但能发现历史交易）

# ---------- 第 4 步：验证导入结果 ----------
bitcoin-cli -regtest -rpcwallet=watch_only getwalletinfo
bitcoin-cli -regtest -rpcwallet=watch_only getnewaddress          # 由描述符派生
bitcoin-cli -regtest -rpcwallet=watch_only listdescriptors        # 查看已导入的描述符
bitcoin-cli -regtest -rpcwallet=watch_only listunspent
bitcoin-cli -regtest -rpcwallet=watch_only getbalances

# ---------- 第 5 步：导入 2-of-3 多签描述符 ----------
# sortedmulti 自动按 BIP67 排序公钥，三方独立导入也能得到同一批地址
MULTI="wsh(sortedmulti(2,[aaaaaaaa/48h/1h/0h/2h]tpubA.../0/*,[bbbbbbbb/48h/1h/0h/2h]tpubB.../0/*,[cccccccc/48h/1h/0h/2h]tpubC.../0/*))"
bitcoin-cli -regtest getdescriptorinfo "$MULTI"      # 拿校验和
bitcoin-cli -regtest -rpcwallet=watch_only importdescriptors \
  '[{"desc":"'"$MULTI"'#checksum","active":true,"internal":false,"range":[0,199],"timestamp":"now"}]'
# 注：BIP48 是多签的路径标准，m/48h/coinh/accounth/scripth，script_type: 1h=P2SH-P2WSH, 2h=P2WSH

# ---------- 第 6 步：热端用 watch-only 钱包构建 PSBT ----------
# walletcreatefundedpsbt 会自动选币、估费、加找零，产出待签名 PSBT
bitcoin-cli -regtest -rpcwallet=watch_only walletcreatefundedpsbt \
  '[]' \
  '[{"bcrt1qexampleaddress0000000000000000000000":0.001}]' \
  0 \
  '{"fee_rate": 15, "replaceable": true, "includeWatching": true}'
# 输出的 "psbt" 字段传给冷端签名

# ---------- 第 7 步：冷端签名后回到热端合并广播 ----------
bitcoin-cli -regtest combinepsbt '["<psbt来自签名方A>","<psbt来自签名方B>"]'
bitcoin-cli -regtest analyzepsbt "<合并后的psbt>"     # 看还缺哪些签名、预估费率
bitcoin-cli -regtest finalizepsbt "<合并后的psbt>"    # 得到 complete=true 与 hex
bitcoin-cli -regtest testmempoolaccept '["<hex>"]'    # 广播前最后一道自检
bitcoin-cli -regtest sendrawtransaction "<hex>"

16.1 PSBT 相关 RPC 速查

RPC对应角色作用
walletcreatefundedpsbtCreator + Updater自动选币、估费、加找零，生成待签 PSBT
createpsbtCreator手动指定输入输出，不含元数据
utxoupdatepsbtUpdater用节点的 UTXO 集补齐输入元数据
walletprocesspsbtSigner用本钱包私钥签名
combinepsbtCombiner合并多份 PSBT 的签名
finalizepsbtFinalizer + Extractor最终化，complete 时直接给出可广播 hex
analyzepsbt诊断显示每个输入缺什么、下一步该谁做、预估费率
decodepsbt诊断把 PSBT 完整展开成 JSON，排查元数据缺失
joinpsbts特殊把多笔不同交易的 PSBT 合成一笔（CoinJoin 用）
调试顺序建议：遇到 finalize 失败时，依次执行 decodepsbt（看元数据齐不齐）→ analyzepsbt（看它说缺什么、next 是谁）→ 检查 witnessScript / redeemScript / bip32Derivation 三项。90% 的 PSBT 问题都是 Updater 阶段漏填元数据。
